## Part 1 — what happened

### Phase 1 — the request, and a first look at the repository
**What the owner asked for.** A "concise skill" for testing:
- red/green/refactor TDD;
- evidence-based root causes, reviewed by an independent subagent;
- a search for similar cases before each fix;
- integration tests, e2e tests and fuzzing;
- Playwright used sparingly;
- review of changes to once-green tests;
- CI economy.

The owner asked for a summary, questions and suggestions, then a wait.

**What I found.** A short survey turned up the things that shaped every later step:
- an existing diagnose-then-review workflow, with 47 root-cause records;
- an "integration" layer defined as real local dependencies, not mocks;
- a CI that never runs the integration or e2e layers.

I asked seven questions and made six suggestions.

### Phase 2 — research by subagents, and the Chromium check
**The owner's reframing.** Codify what earlier sessions did, list the conflicts with it, and audit e2e coverage. The deliverable became a spec, first called v0.2.1.

**What ran.** Two read-only research subagents ran in parallel: an inventory of earlier practice with its conflicts, and an e2e coverage analysis. Both were requested with `run_in_background: false`, but both came back as background tasks.

**Answering "can Chromium be skipped for API-only runs" with evidence:**
- I wrote a two-test Playwright spec, one using `request` and one using `page`, and ran it with `PLAYWRIGHT_BROWSERS_PATH` pointing at an empty directory.
- Getting it to run took three tries. The repo has no `node_modules`, so `@playwright/test` doesn't resolve from the scratchpad. The preinstalled `/opt/node-tools` copy works only when the spec imports `playwright/test`.
- Result: the `request` test passed and the `page` test failed with "Executable doesn't exist".

**The orchestrator convention.** The owner added it mid-phase. It matched prompt §1 of the original implementation prompt.

### Phase 3 — the conflict discussion, D1–D11
**What I presented.** Eleven differences between the request and earlier practice. Several came from retrospective content:
- a draft ADR saying run instructions belong only in the prompt;
- orchestration "lessons" from earlier retrospectives.

**The owner's decisions:**
- A hard rule: retrospective suggestions the owner hasn't adopted are never used.
- Fury at D7, where I had turned "other components mocked" into a new requirement although "I said in passing, once".
- Strict limits on fuzzing.
- Apps get the same testing as the framework. This reversed my D9 framing, which would have kept "apps: API only".
- CI that runs on PRs only, with integration and e2e tests selected by what changed.
- The whole thing to be written as one spec, merged into the v0.2.0 plan, as a standalone file first.

### Phase 4 — the draft, and two independent reviews
**Re-deriving the sources.** I rebuilt the earlier-practice inventory from adopted sources only (the prompt, `plan.md`, `compliance.md`, the CI files), dropping everything retrospective-derived.

**The draft.** The addendum had decisions TS-1…TS-19, a merge map, and the e2e scope.

**The reviews.** Two reviewers ran in parallel.
- **Fidelity:** given the owner's four messages verbatim, it found three major issues:
  - marking scenarios as owner-reviewed would lock them;
  - the retrospective ban missed the copies inside retrospective reports;
  - a fix that failed its re-check had no path.

  It also found invented fuzzing parameters and an invented lint.
- **E2E scope:** it found that the E2E-007 and E2E-008 rewrites need amendments to the owner's own requirements, which the v0.2.0 auth plan doesn't list. Retiring a scenario needs a "Retired" list, or the coverage check keeps expecting its tests. Four proposed additions were already covered.

Everything was applied before the owner saw the draft. PR #55 opened with CI green.

### Phase 5 — the owner's review, and three self-inflicted rounds
**The owner's comments:**
- I had misread "run linters in the harness and pre-commit" as two places. The owner meant one: a Claude Code hook at commit time.
- TS-14 made framework-only statements read as universal.
- O6 was "so damn literal": Claude Code hooks belong to the framework repository, not to app repositories.
- O7 handed the owner a list of requirement IDs to look up.

**My two mistakes in reply.** First, I proposed a new "commit only with git" rule, which the owner rejected. Then I over-corrected: I offered to move already-accepted content into a recommendations list, and the owner rejected that too. The third reply finally listed only what the comments asked for.

**The revision.** It split the spec into common, framework-only and app parts. It also added TS-18 (hooks only in the framework) and TS-21 (pointers name files, not directories), and a plain-words section on the three requirement changes. No fidelity review ran on this revision (Part 3, item 1).

**The follow-up question.** It led to the `CLAUDE.md` change: `docs/README.md` became an index, not a starting read. The owner merged PR #55.

## Part 3 — agents-file suggestions

The remedies below are classified per LESSONS §3 (the amendment's list: (a) mechanical, (b) one-line rule, (c) structural, (d) observation), most preferred first. There are no per-rule `AGENTS-MD-…` files. This repository has no `ai/LESSONS.md`, so the classes are applied as the earlier retrospectives applied them, and nothing is adopted in this PR.

### 1. (b) `CLAUDE.md` line — ideas go to the owner as questions, not into their documents
> "Don't add a requirement, rule, mechanism or number the owner did not ask for to a spec, plan or reply. Ask it as a separate question, and change nothing until the owner answers."

*Grounded in:*
- D7, where a passing "mocked if needed" became a mocking requirement;
- the "commit only with git" rule offered in reply to a linter comment ("I did not ask for that and I do not want it");
- invented fuzz parameters.

It cost three owner messages of correction in this session alone. Asking costs one line.

### 2. (b) `CLAUDE.md` line — what the owner reviewed stands
> "When applying the owner's review comments, change only what they name. Content the owner reviewed without objecting stands; never re-open, revert or reclassify it."

*Grounded in:* after being told to stop inventing, I offered to move already-accepted draft content into a recommendations list. The owner: "I did not ask you to revert decisions I've already made… another example of you doing something I do not want." The rule turns an over-correction into a non-event.

### 3. (b) `CLAUDE.md` line — no bare identifiers to the owner
> "In anything the owner must react to, say in plain words what each requirement, decision or parameter says; never give a list of IDs to look up."

*Grounded in:* O7, "needs amendments to SYS-REQ-018, SYS-REQ-019 and SYS-REQ-027 and COMPL-REQ-006". The owner: "I get extremely upset when you give me a list of object identifiers and assume I know what they are." The plain-words version took a few more lines, and it was what the owner actually reviewed.

### 4. (b) `CLAUDE.md` line — read an instruction by its purpose
> "Read an owner instruction by its purpose in the surrounding discussion. When it has two readings, choose the one that fits that purpose; if neither clearly does, ask before writing either into a document."

*Grounded in:*
- O6, where "hooks only against changes in this repo" was given a file-path reading while the discussion was about framework versus app repositories ("you are so damn literal");
- TS-12, where "linters in the harness … pre-commit" was read as two places.

### 5. (c) Structural — a fidelity review on every revision sent to the owner
**Lesson.** The independent fidelity review caught three major defects in the first draft. The revision made from the owner's comments had no such review, and it drew the same kinds of correction: inventions and over-correction.

**Proposal.** Make the `owner-fidelity-review` skill (Part 2) a required step before any owner-derived document, or any revision of one, is reported as ready.

### 6. (c) Structural — mark each standard's scope
**Lesson.** TS-14 ("apps get the same testing") sat next to rules about this repository's CI, decision log and record paths, all written as if universal. The owner had to point it out.

**Proposal.** In any standard meant for both the framework and apps, the template has three sections: common, framework-only, apps. Every rule sits in exactly one of them, which is how the merged addendum is now laid out.

### 7. (d) Observation — retrospective content leaked into a decision list
Before TS-17 existed, the conflict list D1–D11 drew on a retrospective's draft ADR and its "lessons" as if they were adopted practice. The owner made it a hard rule: retrospective suggestions the owner hasn't adopted are never used. TS-17 now covers it, and its `CLAUDE.md` line is v0.2.0 wave-0 work.

### 8. (d) Observation — Playwright without a browser, and where Playwright lives
- **Playwright without a browser:** a test using only the `request` fixture runs with no browser installed. Only `page`, `context` or `browser` launches one. This is now in TS-11 and §3.5.
- **Where Playwright lives:** in this sandbox the repo clone has no `node_modules`. A scratch spec can use the preinstalled `/opt/node-tools` Playwright only by importing `playwright/test` (not `@playwright/test`), with that `node_modules` linked next to the spec.

### 9. (d) Observation — "foreground" subagents ran in the background
Both research agents, and both reviewers, were launched with `run_in_background: false` or with no flag, and all arrived as background notifications. Plan for the result to arrive later, and don't build a dependent next step into the same turn.
