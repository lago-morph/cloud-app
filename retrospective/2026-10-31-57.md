## Part 1 — what happened

### Phase 1 — the merge request, and a fact check fanned out to four agents

The owner asked for `plan-v0.2.0-testing.md` to be merged into `plan-v0.2.0-auth.md`. The merged file had to be self-consistent, and every change had to be a valid delta from v0.1.1.

**The approach:**
- I read both plans.
- I listed every statement either one makes about the repository as it is today.
- I split those statements into four numbered claim lists: auth code and setup, spec IDs, e2e scenarios and harness, test infrastructure and CI.
- I sent each list to a read-only general-purpose agent, all four in parallel. Each agent answered TRUE, FALSE or PARTLY, with file:line evidence, and returned no file dumps.

**What they found:** all four came back with concise, checkable verdicts, about 25 statements in all that were wrong or only partly right. The testing addendum had already had two independent subagent reviews, one of them "against the repository", and an owner review. It was still wrong in these places:
- **E2E-008:** described as a live owner sign-in. It is an automated `check-login` scenario.
- **E2E-013:** credited with capability-error coverage. It covers API errors.
- **`check-login`'s mail and password steps:** placed in `prodcheck.ts`. They are in the command, `cli/commands/check-login.ts`.
- **DEC-0347, DEC-0319 and DEC-0405:** each described as deciding something it doesn't quite say.
- **The template's browser test:** cited, but it doesn't exist.
- **The root `.claude/settings.json`:** cited, but it doesn't exist.
- **`release.yml`:** said to re-run two tests. It re-runs all of `tests/skill`.

The auth plan (2026-10-26) had its own errors:
- **Deep-link permission IDs:** said to be "looked up from `/tokens/permission_groups`". They are hard-coded in `permissions.ts`.
- **The README:** said to come with v0.1.1. It was added after the release.
- **PAR-241…259:** marked superseded, but PAR-246…249 don't exist, PAR-250…253 are general session parameters, and two related pins (PAR-122, PAR-330) were missing from the list.

### Phase 2 — assembling the merged file, and one destructive slip

While the agents ran, I started writing the merged file. I used Write on `plan-v0.2.0-auth.md` itself with only its new header and §1. That truncated the 336-line plan to about 85 lines. The original came back from `git show HEAD:…`.

From there I built the file the safe way:
1. Each section went into a scratchpad file.
2. Python scripts applied every edit as a `replace` asserted to match exactly once.
3. A final script joined the pieces in order.

**Renumbering:** the testing addendum's cross-references (§3.n → §7a.1.n, §4.n → §7a.2.n, §5 → §7a.3, §6 → §7.1, §7 → §6.1, §8 → §6.2) were rewritten by a regex. The regex skipped references preceded by `CONVENTIONS`, `prompt`, `plan` or `.md`. I reviewed it as a diff before using it, and a grep over every remaining `§n` found the one leftover (`§9 s4`).

**Self-consistency fixes I added:**
- §4.1 now takes `email` from `/user` when the ID token lacks it, which §10 and the e2e list already assumed.
- §3 now says `remove` clears the return-URL registry, which the e2e list tests.
- §4.3 now says `test-` stages run mock login only. Today they also run the password provider.
- §7's automated-pass line now matches E2E-008's new `prodcheck` part.

**Slips my final read caught:**
- I had added "the workers.dev subdomain" to the admin app's account setup (§5.2), copied from an agent's list of setup steps. §5.1 already gives that job to the bootstrap.
- I had added a speculative "(and `check-login`'s, if the auth-app check gets another name)".
- I had added an unverified "or deploy" to when migrations run.

All three were removed before the commit.

### Phase 3 — open points, explained twice

The first summary ended with three open points, in shorthand: "behaviour at role refresh when the auth app is down", "zone groups in the everyday set", and "delete the testing file?". The owner asked: "Explain 1 and 2 more".

The second answer did what the first should have done:
- **Role refresh:** quoted the three places the plan touches it, and laid out the three behaviours as a table with upsides and downsides.
- **Zone groups:** grepped the code to show what each group is used for. Zone Read is used only by a production deploy's email-domain check (`email.ts`, DEC-0553). Analytics Read is used only by `check-login`'s email-delivery check.

That second answer surfaced a gap no one had asked about. v0.2.0's deploy binds Secrets Store secrets, and no group for that was in the everyday set.

**The owner decided:**
- **Role refresh:** fail closed "after a couple of retries".
- **Everyday set:** "drop in needed permissions based on refactor".
- **The Secrets Store gap:** "fill the gap based on your judgement".
- **Files:** delete the testing file, and rename the plan to `plan-v0.2.0-testing-auth.md`.

**Recorded as:**
- §4.1 step 5: two retries, then the session ends and the request is handled as anonymous.
- §5.2 page 2: a four-group everyday set (Workers Scripts Write, Workers R2 Storage Write, D1 Write, Secrets Store Read), each with its reason and its admin-client scope. Three points are marked *unverified* and assigned to the live pass.

The owner asked for a prompt for a new session to implement v0.2.0. It had to run all night without the owner's input and deliver stacked PRs small enough to review. I read the governing prompt's structure, its §10, the CI triggers and the `owner-questions.md` format. The prompt then:

## Part 3 — agents-file suggestions

The remedies below are classified per LESSONS §3, most preferred first: (a) mechanical, (b) one-line rule, (c) structural, (d) observation. There are no per-rule `AGENTS-MD-…` files. The repository still has no `ai/LESSONS.md`, so the classes are applied as earlier retrospectives applied them, and nothing is adopted in this PR.

### 1. (a) Mechanical — a citation check for plans and specs
**Lesson.** Some of the wrong statements were mechanically detectable:
- PAR-246…249 sat inside a "superseded" range, but don't exist.
- `prov/deploy-sequence.test.ts` and `template-pages.ts` were cited by partial paths.
- `.claude/settings.json` was cited as present.

Two reviews missed them.

**Check design.** A script, run in CI on changed `docs/**` and `ai/implementation/*.md` files, would:
- extract every backticked path and verify it exists, or that its line says "new";
- expand every `XXX-NNN…MMM` ID range and report IDs in it that are missing from the decision log, the parameters register or the criteria tables;
- report every bare ID that resolves nowhere.

It can't catch a wrong description of what an ID says; that needs item 2.

### 2. (c) Structural — a claim check before a plan is merged or handed off
**Lesson.** Four parallel read-only agents, each with a numbered list of current-state claims and asked for TRUE/FALSE/PARTLY with file:line evidence, found about 25 errors in under three minutes of wall-clock time. The earlier "review against the repository" was a general review, and it missed most of them.

**Proposal.** Adopt the `verify-plan-claims` skill (Part 2) as a required step before a plan is merged into another, or handed to an implementing session.

### 3. (b) `CLAUDE.md` line — never Write a partial file over the target
> "Build a multi-part rewrite of an existing file in the scratchpad, and write the target only once, complete. Never use Write on the target with part of its new content."

*Grounded in:* the merged header and §1 were written straight over `plan-v0.2.0-auth.md`, truncating 336 lines to about 85. It was recoverable only because the original was committed. Building in the scratchpad costs nothing extra.

### 4. (b) `CLAUDE.md` line — text the owner will paste goes inline
> "When the owner asks for text to use elsewhere (a prompt, a message, a description), put the full text in the reply, in a fenced block. A sandbox file path is not a deliverable."

*Grounded in:* "Telling me the prompt is at a tmp file in your sandbox is not helpful. Output just the prompt text to me now." It cost a round trip at the end of the owner's day.

### 5. (b) `CLAUDE.md` line — an open question to the owner stands on its own
> "When ending a turn with questions for the owner, give each one its context, the options and what each option changes. Don't give a shorthand label."

*Grounded in:* "behaviour at role refresh when the auth app is down" and "zone groups in the everyday set" drew "Explain 1 and 2 more". The full version, with the plan lines quoted, an options table, and what each group is used for in the code, got decisions in one reply. This is the same failure as retro 2026-10-31-55's "no bare identifiers" rule, in another form.

### 6. (c) Structural — when adding a fact from a check, find its current owner first
**Lesson.** A fact copied from an agent's report (setup creates the workers.dev subdomain) was added to §5.2, while §5.1 already assigns it to the bootstrap. My final read caught it.

**Proposal.** In the claim-check skill, every correction records which section of the plan already covers the fact, if any. A correction is applied there, not added as a second statement.

### 7. (d) Observation — the urge to add detail while correcting
Three times in Phase 2, a correction picked up an unrequested, unverified extra: the subdomain, a guess about a script name, and "or deploy". All three were removed. This is the same pattern as retro 2026-10-31-55's suggestion 1 ("ideas go to the owner as questions"). The final read-through is what caught them, so that read stays mandatory.

### 8. (d) Observation — "merge it" still waits for green on the current head
The owner's "merge the PR" arrived while CI ran on a new head. Waiting for that run and merging with `expectedHeadSha` was right: the earlier green was for a different commit.
