## Part 1 — what happened

### Phase 1 — wave 1 in parallel (permissions, token sources, setup record), plus the starter

The owner was away and asked for the whole plan to be implemented, merged and checked live without questions. I wrote three shared files in the scratchpad before launching anything: a common brief (branch, commit trailers, checks, owner rules), the exact exported interfaces each wave-1 batch had to provide (so batch 4 could later consume them without waiting), and a reviewer brief. Batches 1–3 started in one message, each with its own DEC/PAR range. Batch 5 (starter, `version-check`, `upgrade`) was independent, so it started alongside wave 1 instead of after it; the plan's ordering was by dependency, not by phase. Every batch got its own PR and an independent reviewer. Two reviews were FIX FIRST: the `.env.cloudflare` parser kept the template's `(…)` hint text in an uncommented value (batch 2), and `version-check` wrote a mark file in `os.tmpdir()`, which broke "changes nothing" and was symlink-attackable (batch 5). Both went back to the original implementer, red-green, then to the same reviewer for a re-check.

Every parallel branch conflicted with every other in `docs/decisions/decision-log.md` (and later `parameters.md`): each appended a section at the same place. I resolved each by hand in a scratch clone (keep both sides, main's first), which cost a clone, an `npm ci` and a five-minute unit run per merge. Batch 5 also had a real code conflict in `cli/main.ts`, where main had replaced `lazy` with `cloud(...)`; I moved the two new bindings into `wiring.ts` next to the other lazy local bindings.

### Phase 2 — wave 2 (state machine, skill and docs), a container restart

Batch 4 (`cloudflare-setup`) also got the twelve minor findings carried forward from the wave-1 reviews, collected in a scratch file, so the riskiest module absorbed them in one place. Batch 6 wrote the skill, the settings deny rule, QUICKSTART and the spec from the plan while batch 4 was still being built, then re-aligned with batch 4's real messages and exit codes. Mid-wave the container restarted and three agents stopped. Worktrees survived; batch 4 had one local commit not yet pushed, which I pushed before resuming every agent with SendMessage. Batch 4's review found that the success message told cloud users that leaving the deleted bootstrap token in the environment "does no harm", while the next run in fact stopped with exit 1. It also found that two of the twelve carried-forward items had been reported as fixed but had not been.

### Phase 3 — test author, whole-feature review, integration

A separate test author wrote the SETUP/CLI/SKILL criteria tests from the spec. One failed for real: with every setting in the environment, setup created `.env.cloudflare` to fill in two values. An independent agent confirmed the diagnosis before the red-green fix. A whole-feature reviewer (everything since the plan's merge) found a major the per-batch reviews had missed. The skill's first step ran `npx prototype-framework`, an unscoped npm name nobody owns, which in a fresh cloud session would download and run whatever is published under it. It also found that the token guard compared the raw path string, so `..`, backslashes and percent-encoding bypassed it. Combining the guard-fix PR with the tests PR produced a semantic conflict that neither PR's own CI could see: a dangling-symlink test expected `fillInSettings` to create the file, while the SETUP-AC-002 fix said fill-in never creates it. The spec rule won; an integrator agent landed #39, #40 and the review fixes as one PR (#42). An unrelated CI failure on #39 turned out to be a real flake: the AUTH-AC-011 "tampered" token replaced the last two characters with `xx`, which about one time in 1,024 decodes to the same HS256 signature bits.

### Phase 4 — live pass on the owner's account

A guarded API layer was built and unit-tested first, with a read-only preflight of 7 calls. It found that the existing account setup record had no `setupVersion`, so the first live run could not report "nothing to do" as the owner had expected. The first live design used the owner's admin token as the bootstrap stand-in. The re-review saw that the guard's (correct) refusal of its self-delete reached the top-level catch and made every live run exit 1. The fix made the state machine skip the self-delete when the bootstrap ID is protected, rather than allowing the delete. The live pass then exercised everything and found two defects. **D1:** the network check probed the bare `<subdomain>.workers.dev`, which has no DNS anywhere. **D2:** a record-only upgrade reported "nothing to do". It also produced one problem of its own: its driver wrote `frameworkVersion: "unknown"` into the real setup record. Both defects were diagnosed, the diagnoses reviewed independently, and both fixed red-green; a re-check then confirmed exit 0 live and rewrote that one field. Every wizard token was deleted, and Workers, buckets and D1 matched the preflight baseline.

### Phase 5 — release 0.1.1 and README

The release bump broke two things RELEASING.md did not mention. The demo, reference and compliance workspaces also pin the framework, and leaving them at 0.1.0 made `npm install` pull the published 0.1.0 into them instead of linking the workspace. And a harness test hard-coded `"0.1.0"`. The reviewer also caught that the CHANGELOG's upgrade note (`npm run cloudflare-setup`) would fail for 0.1.0 apps, which lack that script. Pushing the tag from the sandbox was refused (HTTP 403; branches push fine), so the owner made the release on GitHub. The first workflow run failed with `OIDC permission denied`: the trusted publisher was not set. After the owner fixed it, the re-run published all three packages with provenance, then failed only at `gh release create`, because the owner's UI release already existed. A root README was added and merged on request.

## Part 3 — agents-file suggestions

Classified per the 2026-06-10 amendment (mechanical check first; no per-rule `AGENTS-MD-…` files). This repository has no `ai/LESSONS.md`, so nothing is added there.

### 1. (a) Mechanical — `release-check` verifies every workspace's framework pin

**Lesson.** RELEASING.md step 1 lists five versions, and `scripts/release-check.mjs` checks the same five. The demo, reference and compliance workspaces also pin `@lago-morph/prototype-framework`. Leaving them at 0.1.0 made `npm install` silently fetch the published 0.1.0 into those apps instead of linking the workspace, so their checks would have tested the old release. It was caught only by reading the lockfile diff.
**Check design.** In `versions()`, add every workspace `package.json` (read the root `workspaces` list) that depends on the framework. Also fail if `package-lock.json` holds any `registry.npmjs.org/@lago-morph/` tarball. Update RELEASING.md step 1 to say "every workspace pin".

### 2. (a) Mechanical — no hard-coded release version in tests

**Lesson.** `tests/compliance/harness/node-deps.unit.test.ts` asserted `"0.1.0"` for the installed framework version and broke CI on the bump. **Check design:** a unit test that greps `*.test.ts` for the current `packages/framework/package.json` version string next to `@lago-morph/prototype-framework` and fails, so tests read the version from the package instead. Allow fixtures through an explicit list.

### 3. (a) Mechanical — the release workflow tolerates an existing GitHub release

**Lesson.** The owner created the release in the GitHub UI, which pushed the tag. The workflow then published to npm and failed on `gh release create` ("Release.tag_name already exists"), leaving a red run after a successful publish. **Check design:** in `release.yml`, use `gh release view "$TAG"` and then either `gh release edit --notes-file` or `gh release create`. This goes through `.github/workflows-patch/`, since sessions cannot push workflow files.

### 4. (a) Mechanical — a union merge for append-only registers

**Lesson.** Every parallel batch conflicted in `docs/decisions/decision-log.md` and `docs/parameters/parameters.md`, about eight hand resolutions, each followed by a clone, an `npm ci` and a five-minute unit run. **Check design:** `.gitattributes` with `docs/decisions/decision-log.md merge=union` and `docs/parameters/parameters.md merge=union`. Keep the existing duplicate-ID test as the guard against bad unions; it caught nothing here, but union order could interleave table rows. Owner's call, since union merges can also hide genuine edits to the same entry.

### 5. (b) `CLAUDE.md` line — cloud sessions can't push tags

> "Cloud sessions can push branches but not tags (403). Release tags are created by the owner; prepare and merge the release PR, then hand over the exact tag command."

*Grounded in:* five retried `git push origin v0.1.1` attempts that each returned `RPC failed; HTTP 403`, after which the owner tagged by hand. The facts stated are true of this environment, and the rule is one line.

### 6. (b) `CLAUDE.md` line — live drivers call the product's own entry points

> "Scripts that drive a live check call the same entry points the CLI uses (with the same inputs), never re-implemented calls; anything they write to a real account must be what the product would write."

*Grounded in:* the live driver called `applySetupSteps` without `frameworkVersion`, so the owner's real setup record got `frameworkVersion: "unknown"`, and later runs would not correct it. It needed a second live write to repair.

### 7. (c) Structural — integrate parallel PRs that touch the same module before merging either

**Lesson.** #39 (guard fix, with a dangling-symlink test) and #40 (SETUP-AC-002 fix: fill-in never creates the file) were each green alone, but red together. This was found only because I merged one into the other locally. **Proposal:** when two open PRs touch the same file, run the unit tests on their combination before merging the first, or turn on GitHub's merge queue so every merge is tested against the real base.

### 8. (c) Structural — a sandbox environment reference document

**Lesson.** Facts rediscovered or newly found this session:
- the pre-installed Chromium is build 1243 while Playwright 1.64.1 wants 1248, and a `PLAYWRIGHT_BROWSERS_PATH` symlink shim fixes it;
- a token created seconds earlier can get a 401 on its first read;
- the bare `<subdomain>.workers.dev` has no DNS;
- the proxy status endpoint prints recent hosts in clear text, including the subdomain;
- tags can't be pushed;
- npm trusted publishing needs the publisher configured per package.

The previous retrospective proposed `ai/environment.md` "once a second prompt or skill needs them". The live-pass skill spec here now needs them. **Proposal:** create it.

### 9. (d) Observation — an agent claimed fixes that weren't there

Batch 4 reported "review findings 1–12 fixed", but its reviewer found items 10 and 11 untouched. No new rule: independent review with an explicit checklist of the claimed items is what caught it. The orchestrator should keep passing the numbered list to the reviewer.

### 10. (d) Observation — the orchestrator's shell drifted into an agent worktree

One `cd` into a worktree to push a recovered commit left later commands running there. The stop hook then flagged that agent's untracked files as mine. Use absolute paths, or a subshell, for one-off worktree commands.
