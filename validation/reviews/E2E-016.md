### Check 2: no capability contract references another capability's adapter

The evidence for PASS:
- **Contract files.** `docs/contracts/ts/*.d.ts`, `internal/login-provider.d.ts` and `http/framework.openapi.yaml` contain no target or adapter names. Searching for `cloudflare|d1|r2|wrangler|miniflare|pglite|workerd|aws|sqlite|postgres` finds only `sql.d.ts:5` ("Postgres-flavoured types", the contract's own typing basis) and the provider-neutral comment in `internal/login-provider.d.ts:3,28`. The words "target", "dialect" and "adapter" appear only neutrally (core.d.ts:16,70; sql.d.ts:87,114,141; testing.d.ts:17,26).
- **Capability `public.ts` files.** auth, config, files, http, kv, log, secrets and sql import only `hono` types, `zod`, `drizzle-orm` operators, their own modules, and `core/errors.js`. `core/public.ts:7-13` imports only other capabilities' `public.js` contract types. No `public.ts` imports a `local/`, `cloudflare/`, `d1`, `r2` or `pglite` module of another capability. `mig/public.ts:7` names MIG's own `d1MigrationDatabase` and `pgliteMigrationDatabase` in a comment, with no export.
- **Exports match the contracts.** A scripted comparison found that the hubs' exported names equal the contract names exactly: `src/index.ts` against index/core/errors/http/sql/kv/files/config/secrets/log/auth.d.ts, `src/client/index.ts` against client.d.ts, and `src/testing/index.ts` against testing.d.ts. No extra names and no missing names. `package.json` `exports` lists exactly the CORE-REQ-005 subpaths for this phase.

Non-blocking observations (implementation or target level, not contracts):

**R-02: LOCAL's subpath type comes from the Cloudflare target module.** Non-blocking. Owner: B-16 (LOCAL target).
`packages/framework/src/targets/local/public.ts:21,24` imports `WorkerHandler` and re-exports it from `../cloudflare/bindings.js`. local.md documents that the local runtime reuses the Cloudflare adapters, so this is by design. Still, `./targets/local`'s declared surface depends on a Cloudflare module. A neutral home for `WorkerHandler` would keep a future non-Workers local runtime from inheriting a Cloudflare type.

**R-03: The FILES local adapter imports a helper from the FILES Cloudflare adapter directory.** Non-blocking. Owner: D-02 / FILES.
`packages/framework/src/files/local/route.ts:12` imports `downloadDisposition` from `../cloudflare/disposition.js`. The helper is target-neutral (disposition.ts:1-6), and DEC-0329 (decision-log.md:2591) records the placement as an ownership workaround. Both directories belong to one capability, so check 2 is not violated. A neutral FILES module would remove the cross-target dependency.

**R-04: KV reaches into SQL's internal adapter registry.** Non-blocking. Owner: B-08 (KV).
`packages/framework/src/kv/service.ts:10,36-38` uses `adapterOf(db)` from `sql/handle.js` to obtain the dialect. It does not import a target-specific SQL driver, and kv.md:42 documents the SQL-table backing. Because it depends on SQL's internal handle rather than the `PortableDb` contract, a change to SQL's handle representation also changes KV.

**R-05: SEC's internal-secret registry names a FILES Cloudflare-adapter credential.** Non-blocking. Owner: B-10 (SEC) with D-02.
`packages/framework/src/secrets/names.ts:22-24` and `docs/components/secrets.md:51` list `frameworkR2AccessKeyId` and `frameworkR2SecretAccessKey`. This is a framework-internal registry, not the app-facing `secrets.d.ts`, which is clean. Each new target's FILES credentials would still require an edit to SEC.

### Check 3: no design adds features beyond its requirements

I compared the app-facing surface (contracts and implementation, which match exactly; see check 2) with each component's REQ list. Every exported name traces to a REQ or the design it cites. Examples: `requireCurrentUser` (AUTH-REQ-004, auth.md:27), `queryParams` (HTTP-REQ-003), `configStringList` (CFG-REQ-001), `containsText` and `countDistinct` (SQL-REQ-002, sql.md:25-26,94-95), `head` (FILES-REQ-001), and `getCurrentUser`/`login`/`logout` (auth.md:5). The implemented CLI commands (cli/main.ts:36-48) match the CLI-REQ-001 table (cli.md:14-26) one for one. `stopApp`/`startApp` trace to MIG-REQ-006 and PROV-REQ-002 step 6 (provisioning.md:91). The template's finalize route and HMAC helper are required by skill.md:77-78.

**R-06: Raster-image `inline` download disposition is beyond FILES' requirements and behaves differently on local and Cloudflare.** Blocking. Owner: FILES (D-02 for files.md and the Cloudflare part; B-11's `src/files/service.ts`).
FILES-REQ-001…006 (files.md:9-49) say nothing about download names or disposition. DEC-0313 (decision-log.md:2433-2436) itself says "files.md does not say what name a download gets". Naming the download after the file fills that gap. Choosing `inline` instead of `attachment` for raster images is an added behaviour that no requirement asks for. As implemented, it also diverges by target:
- local: `files/local/route.ts:46` passes the stored content type, so raster images download `inline`;
- Cloudflare: `files/service.ts:43,150` calls `tickets.download(name)` with no content type, so `files/cloudflare/tickets.ts:83` always signs `attachment`. files.md:65 documents this ("`inline` only when the service passes the file's content type … `attachment` otherwise"), and DEC-0329 (decision-log.md:2591) leaves the service change open ("Until then, Cloudflare names raster images `attachment`").

Both DEC-0313 and DEC-0329 are "owner review open". Resolution belongs to the owning items. One option is to drop the raster-`inline` branch so every target sends `attachment; filename*=…`. The other is to have the owner accept the behaviour as a requirement and complete the `service.ts` wiring so the targets agree. Related: DEC-0313's status line (decision-log.md:2434) still says "not yet implemented", which is stale (disposition.ts:30 exists).

**R-07: `remove --confirm-production <s>` is an option CLI-REQ-001 and PROV-REQ-003 do not list.** Non-blocking. Owner: D-05 (cli.md §2 text at cli.md:87; `cli/commands/remove.ts:2,29`).
CLI-REQ-001 (cli.md:22) and PROV-REQ-003 specify `remove --target <t> --stage <s>` for "the named stage". DEC-0350 (decision-log.md:2833-2836) adds a production-confirmation option and refuses unconfirmed production removal. The option narrows behaviour for safety and is recorded, but it changes a binding command's interface. It stays open until the owner accepts it or chooses "refuse production stages entirely", as DEC-0350 itself asks.

**R-08: `generate-migration [--name <slug>]` is an option CLI-REQ-001 does not list.** Non-blocking. Owner: B-17 (cli.md:83; `cli/main.ts:39`) and B-07 (DEC-0142, migrations.md:41).
The slug is cosmetic and defaults to `schema`. It is traceable to DEC-0142 (decision-log.md:1107) but not to a REQ. Either keep it as recorded design or drop it.

**R-09: `PROTOTYPE_FRAMEWORK_ABORT_AT` is a runner-only hook in the shipped `deploy` command.** Non-blocking (traced). Owner: D-05 (`cli/commands/deploy.ts:5,42`).
It traces to COMPL-AC-008 and compliance.md:67 through DEC-0269 and DEC-0352. I record it because it is test behaviour present in production code. It is not a feature beyond requirements.
