## Group: test-was-wrong — the test helper `record()` ordered the migration record by `applied_at`, which ties within a millisecond
Cites: ai/implementation/root-causes/2026-10-31-C-mig-record-order-tie.md (Review: accepted-with-changes, `session_014mWQ6ioY6LQtpv18AcSoU8`, round 1 answered); `docs/components/migrations.md` MIG-REQ-002 (framework migrations first, then app migrations, in order)
Tests:
- `packages/framework/src/mig/apply.unit.test.ts` — helper `record()` used by "[MIG-AC-002] a fresh database gets the framework migrations, then the app's, each recorded once in order …", "[MIG-AC-002] a second run with nothing pending …" and "[MIG-AC-003] local: a data-dependent failing migration … a re-run after correcting the data succeeds" (sqlite and postgres) — the query's order `ORDER BY applied_at, id` → `ORDER BY CASE WHEN id LIKE 'framework/%' THEN 0 ELSE 1 END, id` (expected results unchanged)
Verdict: accepted
Reasons:
- The root cause is accepted and says exactly this. Two neighbouring migrations recorded in the same millisecond tie on `applied_at`. The `id` tie-break puts `app/…` before `framework/…`, so the test's read order, not the apply order, was wrong. The record reproduces the CI diff exactly with a 1, 2, 3, 4, 4 clock. No production code orders the record by `applied_at`.
- The new order is the one the spec defines (MIG-REQ-002: framework first, then app). Within each history, `id` order is the apply order, because the IDs carry the zero-padded migration number. That is what the reviewer's finding 5 asked for, and it fixes the same latent tie in both MIG-AC-002 tests, as finding 5 required.
- Not weakened. The expected lists are the same exact `toEqual`s. One thing is no longer checked implicitly: the old order also checked that `applied_at` does not decrease in apply order. The new test now checks it explicitly with an injected clock. It is "[MIG-AC-002] the record lists the framework migrations, then the app's, even when two neighbouring migrations share applied_at" (clock 1…n, n). It asserts the exact `applied_at` of every row, framework 1…n then every app row n, so `applyMigrations` must read the clock once per migration in apply order. It also asserts the exact ID order under the tie.
- Red→green is shown by the two commits. The red commit adds the tie test first. It fails with the old `record()`, as in the root cause's verification plan. The green commit changes only the helper.
