## Group: behaviour-changed — the everyday token's delete guard keeps the last everyday token
Cites: DEC-0715 as amended in `77e0d48` ("Before any DELETE, the IDs are checked against the list of everyday tokens and the 32-hex shape, and the last everyday token is never deleted"); review of PR #104 (minor finding 3); plan-v0.2.0 §5.2 page 2 (create a new token, then delete the old one after the person has saved it)
Tests:
- `packages/framework/src/provision/cloudflare/everyday-token.unit.test.ts` — "deletes the named old tokens that are everyday tokens, and refuses any other ID" — setup changed: the fake account now also holds the new everyday token (`"e".repeat(32)`, `everydayPolicies(A)`), as the real fallback leaves it; the call, the expected `{ deleted: [old.id], skipped: [other.id, "../x"] }`, the token-store checks and the exact `writes` list are unchanged
Verdict: accepted
Reasons:
- The reason holds. The code now refuses to delete the last everyday token (`everyday.size - deleted.length <= 1` in `deleteOldEverydayTokens`). The old setup had the old token as the only everyday token, so the old expectation (`deleted: [old.id]`) would now be wrong. The decision text and the code agree.
- Not weakened. Every assertion is the same, and still exact (`toEqual` of the result and of `f.writes`). The setup now matches the state the function really runs in: after the fallback, the account holds the old token or tokens and the new one. A setup that hides the new token would test a state the page never produces.
- The new behaviour has its own test: "never deletes the last everyday token" (one everyday token, asked to delete it, `deleted: []`, `skipped: [id]`, token kept). Together the two tests cover both sides of the guard. Sampled with them, all new in `77e0d48`: "only a refusal (403) falls back …", "with several tokens, every one is read before any is written …" and "refuses to work from a token list longer than it reads …". They cover the other two DEC-0715 amendments, and none of them changes a once-green assertion.
- One edge left untested, not part of this change: deleting two old tokens while a third (the new one) exists, where the guard must still allow both deletes. The guard's arithmetic allows it (`3 − 0 > 1`, `3 − 1 > 1`), and the page deletes old tokens only after the new one exists.
