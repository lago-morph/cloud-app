Verdict: accepted-with-changes
Reasons:
- **minor**: for `password-no-leak.test.ts`, `pwd/support.ts` and `admins.ts`, the reason holds. The password provider and `mail last` went in B 45 and 46. These tests could no longer run, and the helpers had no other users. SEC-AC-002's other clauses keep their tests on this branch:

  - `test/integration/secrets/secrets.test.ts` and `cli.test.ts`;
  - `targets/cloudflare/worker.unit.test.ts`.
- **minor** (binding, for D or T6; spec only): SEC-AC-002's text (`docs/components/secrets.md` line 73) still says "locally, they also contain no … test password, verification token or reset token of the password provider". The text is unchanged on 57z and on `39b-spec-followups`. That clause now has no test and no code. Drop it from the criterion, as was done for PROV-AC-004's email clauses (DEC-0698).
- **minor** (finding for T6, lost check where the code stays): PROV-AC-004's prodcheck ticket round trip. The rest of this reason gives the analysis, the restoring test, and why the test is not blocked.
  - What the round trip proved, and nothing else proves now: the R2 signing credential that a setup-account **re-run** writes (DEC-0550 "Re-run of setup-account" replaces the token) is accepted by R2. It also showed that a stage deployed afterwards signs tickets with it that R2 accepts, for both upload and download.
  - The code it covered stays:
    - `createAccountSigningCredential`'s replacement path in `provision/cloudflare/r2-token.ts`;
    - deploy's copy or binding of the credential (`target.ts` `ensureFrameworkSecrets`, `signingBindings`);
    - the ticket signing in `files/cloudflare/tickets.ts` and `files/s3/sign.ts`.
  - What still covers it (`git grep -n` on this branch):
    - unit: `files/s3/sign.unit.test.ts` (SigV4 against the published presigned example); `r2-token.unit.test.ts` ("setup-account creates one token … a same-named token without a record is replaced", "the old signing token is deleted only after the new token and its record exist", and the Secrets Store placement); `targets/workers.unit.test.ts` (tickets through a Worker);
    - cloud: FILES-AC-003 (`criteria/files/transfers.spec.ts`, a real-browser upload and download through tickets on the run's test stage) and FILES-AC-005; CF-AC-002 (`cf/stage-resources.test.ts`: both stages' tickets carry the record's access key ID);
    - in the re-run clause itself: `signingCredentialProblems()` (the record is complete, exactly one token, which is the record's, with DEC-0550's policies), the token ID changed, the old token deleted, and the prodcheck redeploy exits 0.
  - So the signing code is still covered. A ticket R2 accepts is shown on every cloud run by FILES-AC-003, with whatever credential the account holds. CF-AC-002 compares access key IDs only, and does not show that R2 accepts the ticket. What is lost is narrower: in the re-run clause, nothing now shows that the **new** credential works. The cloud check `signingCredentialProblems()` (`setup-account.test.ts:138`) reads the record, the token list and the policies, but never signs anything. A wrong `secretAccessKey` written by a re-run would pass the clause. The clause's `finally` would not catch it either. It finds no problem, so it neither restores nor fails loudly. Restoring would be impossible anyway: the re-run deletes the old token (`:279`), and the restore runs only while that token exists (`:290`). So a broken new credential would stay on the account, unreported. It would surface only as FILES-AC-003 failures in the next cloud run, blamed on FILES.
  - The test that restores it does not need a production-stage sign-in. A test stage signs tickets on the same path as `prodcheck` (`target.ts` makes no production-specific choice of credential), and a test stage signs in through `mock-login`. Restore it in the re-run clause of `tests/compliance/criteria/prov/setup-account.test.ts`, after `refreshProdcheck`:
    - deploy a further `test-<random>` stage of `apps/reference` with `withCloudStage` (as CF-AC-002 does), signed in with `stage.client().as("user")`;
    - request an upload ticket and assert that its `X-Amz-Credential` access key is the new record's `tokenId` (CF-AC-002's `signing()` parse);
    - PUT the bytes (2xx), then GET them through a download ticket (200, the same bytes), and delete the file;
    - make a failure there count as a problem in the `finally` block, so that the clause ends with the loud "THE ACCOUNT'S R2 SIGNING CREDENTIAL IS BROKEN … Repair it now with: <REPAIR_COMMAND>" failure (`:296-298`). It cannot restore the old record, because the re-run has already deleted the old token (evaluator's correction).
    - Suggested title: `[PROV-AC-004] a re-run of setup-account replaces a signing record …; a stage deployed afterwards signs tickets with the new credential that R2 accepts (upload and download)`. It needs one more deploy with D1 (`requireCloudD1`).
    - The prodcheck redeploy can stay. The progress note's "needs a production-stage sign-in for tests (T1/T2)" is then no longer a blocker for this check.
- **minor** (advisory, T6; already listed): `cli/support/admins.ts` is now imported only by `compl/prodcheck.test.ts` (`recordedOrigin`). It could move next to its user. Its header still describes CLI-AC-006/007 and `admins`.
