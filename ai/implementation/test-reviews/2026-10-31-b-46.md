Cites: plan-v0.2.0 §4.1 (production stages sign in through the auth app) and §6; DEC-0670 (check-login's IDs: E2E-008, AUTH-AC-011, PWD-AC-009 `not-run`); DEC-0696 (PWD-AC-009 retired); T5 batch-1 assignment of `criteria/compl/prodcheck.test.ts` to B (`progress-v0.2.0.md` Open items)

- `tests/compliance/criteria/compl/prodcheck.test.ts` — COMPL-AC-005 "after this run redeployed prodcheck …" — the three PWD-AC-009 assertions (in `CHECK_LOGIN_IDS`, a `[PWD-AC-009]` driver check, expected on every automated cloud run) → one assertion that the driver lists a `[E2E-008]` check
Verdict: accepted-with-changes
Reasons:
- **minor**: the redirect assertion is rewritten for the new provider and is no weaker. It checks the path and the exact `return`, as AUTH-AC-011 and DEC-0667 define them. The origin of `/start` is not compared, because the app has no recorded value to compare it with (DEC-0670). The `PRODCHECK_IDS ⊇ COMPL-AC-005` check stays.
- **minor**: replacing PWD-AC-009 with E2E-008 is right. PWD-AC-009 is retired, and `check-login` now records it only as `not-run`. E2E-008 is the criterion its passing run proves (DEC-0670). The dropped "expected on every automated cloud run, with no not-run rule" check has no equivalent for E2E-008. `release.unit.test.ts` ("the provider check's automated part (AUTH-AC-011, E2E-008) is automated on Cloudflare") covers it against the documents' catalogue.
- **minor** (finding for T6, lost function; code and fixtures outside B's paths): PWD-AC-009 is still wired into the harness and the release tool.
  - `tests/compliance/harness/prodcheck.ts` keeps `CHECK_LOGIN_IDS = ["PWD-AC-009", "AUTH-AC-011", "E2E-008"]`, and `PRODCHECK_IDS` still lists the retired MAIL-AC-006 and CLI-AC-007. The driver's fold is asserted with PWD-AC-009 `passed` fixtures in `driver.unit.test.ts`, which is why B left the ID in (B's note 4, assigned to T5/T2). Harmless on its own: the catalogue no longer has the ID.
  - **It breaks the release report.** `tests/compliance/tools/release.ts` finds "the last passing check-login record" by `LOGIN_CHECK = "PWD-AC-009"`, all entries `passed`. From 43 on, `check-login` writes PWD-AC-009 as `not-run`, so no real record can match. The release report will always print "No passing check-login record (PWD-AC-009)" and list every commit since the start. `release.unit.test.ts` stays green only because its fixtures still record PWD-AC-009 `passed`, which the real command can no longer produce.
  - **The fix** (for the harness and tools owner, after T6 confirms): set `LOGIN_CHECK` to AUTH-AC-011 or E2E-008, and update `LOGIN_PROVIDER_PATHS`, which names the deleted `auth/password/`, `mail/` and `auth-password.openapi.yaml`. Then drop PWD-AC-009 from `CHECK_LOGIN_IDS`, from `check-login`'s record and from `driver.unit.test.ts`'s fixtures, and drop MAIL-AC-006 and CLI-AC-007 from `PRODCHECK_IDS`.
- **minor** (advisory, the file owner): the header comment of `prodcheck.test.ts` (lines 12–21) still says `/api/auth/login` redirects to `<public origin>/api/auth/sign-in` and that the run "folds PWD-AC-009 in".
