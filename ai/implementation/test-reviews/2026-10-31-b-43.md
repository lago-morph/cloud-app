Cites: plan-v0.2.0 §6 (check-login's steps) and §6.1 item 3; §7.1 E2E-008; DEC-0670 (B: "All eight old steps were password, mail or `admins` steps, so they go"; three HTTP steps; no Cloudflare credential); DEC-0692 (D: `check-login` is the automated part of the provider check); AUTH-AC-011 as rewritten by D (DEC-0694, `docs/components/auth.md` §4); `docs/components/cli.md` CLI-REQ-001 row for `check-login`

Verdict: accepted-with-changes
Reasons:
- **minor**: the reason holds. Every removed case drove a step that no longer exists: password sign-up, verification, sign-in, reset and the PAR-258 burst (PWD, retired by DEC-0696), the mail sink and Email Sending analytics (MAIL, retired), and the `admins` grant and revoke (CLI-REQ-005, retired by DEC-0698). The new `check-login.ts` has no such code (read in full), so no removed assertion checked behaviour that stayed.
- **minor**: what stayed is still checked as strictly. The refusals (local target, test stage, bad stage name, unreachable proxy, dirty tree, no deploy output) keep "no request and no record". One dispatcher for every request, the forged `X-Forwarded-Host` and the DEC-0086 subdomain redaction are now asserted in the passing test. The per-step failure table checks the exit status, the step number, the exact message, the record path and the E2E-008 detail for every fault.
- **minor**: the new steps are covered against AUTH-AC-011's rewritten text, sampled clause by clause: the redirect to `/start` (`start-elsewhere`, `relative-start`, `http-start`), the app ID (`wrong-app`, `two-apps`), the `return` on the recorded public origin despite a forged host (`callback-on-forged-host`), the `state` (`no-state`), the transaction cookie (`no-login-cookie`), and the bogus-code callback (`bogus-code-not-redirected`, `bogus-code-signs-in`). The AUTH-AC-011 status follows steps 1–2 only (`step <= 2 ? "failed" : "passed"`), as DEC-0670 states. Step 3 (the auth app's registry) has five faults.
- **minor** (binding, for B or T6): one branch of step 2 has no fault case: "after the bogus callback: `/api/auth/me` is not anonymous". It is AUTH-AC-011's last clause ("leaves `/api/auth/me` anonymous"). Add a fault whose stage answers `/api/auth/me` with a non-anonymous level and expect step 2 to fail with that message.
- **minor** (binding, for B or T6): the old passing test ran `expectNothingSecret` over the output and the record. The new passing test only checks the redaction of the subdomain; the failure cases check that the auth app's `state` is not printed. `cli.md` says the command "prints no token". Add to the passing test a check that neither the `__Host-login` cookie value nor the app's `state` appears in the output or the record.
- **minor** (advisory, T2): `docs/acceptance/e2e-scenarios.md` E2E-008 still describes the password steps ("sign-up with real email delivery …"). The test now follows DEC-0670 and AUTH-AC-011, not that scenario text. T2 rewrites the scenario (plan §7.1); until then E2E-008's test and its scenario disagree.
- **minor** (advisory, T6): `check-login` still writes `PWD-AC-009` as `not-run`, and `tests/compliance/harness/prodcheck.ts` still lists it in `CHECK_LOGIN_IDS`. That is intended until the harness drops it (DEC-0670), but `tests/compliance/tools/release.ts` still uses `LOGIN_CHECK = "PWD-AC-009"` as "the last passing check-login record". After this PR no real record can pass PWD-AC-009, so the release report will always say "No passing check-login record". `release.unit.test.ts` stays green only because its fixtures still record PWD-AC-009 as `passed`. See the finding in the 46 record.
