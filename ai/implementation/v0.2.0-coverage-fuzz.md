## 2. Fuzz targets (§7a.1.7)

**Tool (DEC-0645): `fast-check` 4.10.2, pinned exactly (PAR-410).** Each target calls `fc.assert(property, { seed, numRuns })` inside an ordinary Vitest test named `*.fuzz.unit.test.ts`, placed beside its module. Why this tool:
- It is pure JavaScript: MIT licence, one dependency (`pure-rand`), no native build.
- It runs offline in Node and in the Workers-compatible code paths.
- It shrinks failures and prints the seed and path of a failing case.
- It was published 2026-09-19, more than two weeks before this run.

Checks done for this file:
- **Lockfile:** `package-lock.json` holds no fuzz tool today. No `fast-check`, `pure-rand`, `@fast-check/vitest` or `@jazzer.js/*`.
- **Registry:** `npm view fast-check` works through the proxy (4.10.2, `dependencies: { pure-rand: ^8.0.0 }`, `engines.node >=12.17.0`).
- **Offline run:** fast-check 4.10.2 was installed into a scratch directory. A seeded property over `sanitizeReturnTo` then ran 1,000 cases with the proxy variables unset, in 0.7 s on Node 22.23.4.

Tools rejected:
- `@jazzer.js/core` 4.0.0 needs a native build (`cmake-js`, `node-addon-api`).
- `zod-fast-check` 0.10.1 needs zod 3 and fast-check below 4, but the repo has zod 4.6.7. G 68 maps zod 4 schemas to arbitraries itself.
- `@fast-check/vitest` 0.5.0 is pre-1.0 and adds nothing to a plain `fc.assert`.

**Run count and seed (DEC-0647):**
- **Seeds:** a fixed integer literal per target, `20261031nn`.
- **Run count:** 1,000 by default (PAR-412). A target that runs fewer states why.
- **Time budget:** at most 1 s per target on the CI runner, and 10 s for all framework targets in `npm run test:unit` (PAR-411).
- **Failures:** a failure goes through §7a.1.8, and the shrunk counterexample becomes a plain regression test.

**Considered and not chosen (DEC-0648):**
- **`files/disposition.ts` `downloadDisposition`.** It encodes byte by byte and is total by construction, and example tests cover it. Its rule changed four times (DEC-0313/0329/0414/0535), but over policy, not through regressions.
- **The CI classifier's path matcher (S3).** Its input is repo paths from git, not a trust boundary, and S3 sends unmatched paths to every layer.
- **`http/validation.ts` (`jsonBody`, `queryParams`).** A thin wrapper over zod. Apps' request schemas get G 68's helper.
- **The auth app's ID-token claim checks.** A library does the signature and parsing, and the claims are fixed comparisons that examples cover.
- **Stage and app name rules.** The input comes from the owner's CLI, not an untrusted party.
- **The compliance `Where` and catalogue readers.** They had a repeated regression (COMPL-AC-001 root cause), but they are internal docs parsers, not a trust boundary.
