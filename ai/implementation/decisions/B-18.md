# Decision drafts — B-18 (template app)

Taken under the owner's "make an assumption and continue" instruction; open for review.

### DEC-PENDING-B-18-1 — What the template contains, one use per capability
Origin: ai-proposed · Status: accepted · Affects: SKILL-REQ-004, skill.md §2 "The template", cli.md §2 "App layout", CHECK-AC-005, E-02, C-05

`apps/template` (app name `template`) is a notes app: config key `greeting` (`GET /api/hello`, anonymous); SQL table `notes` (`GET`/`POST /api/notes`, user's own rows, `requireUser`); a log entry per created note (component `notes`); KV status line per user (`GET`/`PUT /api/status`); files in `users/<id>/` via upload/download tickets (`GET /api/files`, `POST /api/files/{upload,download}-ticket`); one secret `apiKey`, checked (never returned) by an admin-only route (`GET /api/admin/secret`, `requireAdmin`). One route module per capability in `src/server/routes/`, each taking `Hono<Env>`; `src/server/env.ts` exactly as skill.md §2. The browser part is `index.html` at the app root (the Vite root, as in B-T4's base fixture) plus `src/client/main.ts` and one page module per capability under `src/client/pages/`, built with `textContent` only. `src/shared/types.ts` holds only types: the portability rules let browser code import shared code type-only (DEC-PENDING-B-14-2), so input limits live in the server's Zod schemas only. `config/local.json` and `config/cloudflare/test.json` set no values (the greeting has a default) and an empty `framework` section. Only `.`, `./client` and `./testing` are imported; nothing names a target.

### DEC-PENDING-B-18-2 — The smoke file picks its mode through the test runner's provided context
Origin: ai-proposed · Status: accepted · Affects: CLI-AC-005, skill.md §2 "Testing", testing.d.ts `connectTestStage`, C-04

`tests/smoke/smoke.test.ts` calls `connectTestStage()` when Vitest's `inject("prototypeFrameworkSmoke")` is `true`, and `createTestApp(app, …)` otherwise (so it runs in-process under `verify`). App code may not read `process.env` or `import.meta.env` (`no-env-access`), and the contract has no other switch, so the runner's provided context (PAR-116 is Vitest) is the simplest target-neutral signal. **For C-04:** `smoke` must run Vitest with `provide: { prototypeFrameworkSmoke: true }` on `tests/smoke/**`. If C-04 prefers another mechanism, only this file changes. The smoke checks avoid `logs()` (throws on a connected stage) and use a fresh random mock user per run, so they also pass on a stage that keeps data.

### DEC-PENDING-B-18-3 — Committed migrations generated with MIG's generator; app test timeouts
Origin: ai-proposed · Status: accepted · Affects: MIG-REQ-001, CLI-REQ-002, B-17

The CLI was not merged, so `migrations/` (`0000_schema` pair, snapshots, `checksums.json`) was generated by calling MIG's `generateAppMigrations` on the loaded app (the engine `generate-migration` uses); the migration checker reports nothing. `vitest.config.ts` keeps the PAR-116 glob and raises test and hook timeouts to 60 s, because the first PGlite open in a Postgres-dialect process takes over 5 s (observed: the first test timed out at the default). **For B-17:** `verify`'s test runs must either use the app's `vitest.config.ts` or apply an equivalent timeout themselves.

### DEC-PENDING-B-18-4 — The template imports `hono` types without declaring `hono`
Origin: ai-proposed · Status: accepted · Affects: skill.md §2 ("route modules take `Hono<Env>`"), B-01 dependency rule, C-05

Route modules use `import type { Hono } from "hono"` as skill.md prescribes; `hono` is a framework dependency, resolved by hoisting. Adding it to `apps/template/package.json` would change the shared lockfile, which only an integrator regenerates (plan §9.2). Proposed (integrator or CORE): either declare `"hono": "4.13.13"` (PAR pin) in the template's dependencies and regenerate the lockfile, or re-export the `Hono` type from `.` so apps need no direct `hono` import. Scaffolded apps installed from a tarball depend on hoisting until then.
