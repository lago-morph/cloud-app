### DEC-0630 — What the root-cause record lint checks, and that it applies to every staged record

Origin: ai-proposed · Status: accepted · Affects: plan v0.2.0 §7a.1.8, §7a.2.5; plan.md §10.5; `scripts/lint-records.mjs`

The plan names the required sections and "a Review verdict or `Status: awaiting review`" (§7a.2.5) and the three verdicts with reasons marked **major** or **minor** (§7a.1.8 step 2). The lint makes that checkable:
- The seven sections (Symptom, Evidence, Causal chain, Alternatives ruled out, Proposed fix, Verification plan, Review) are level-2 headings, matched by prefix and case-insensitively, so `## Proposed fix (not applied)` counts but `### Evidence` (a subsection) and `## Evidenced …` do not. Each has content; subsection text counts. Headings inside fenced code are ignored.
- The verdict and the status live in the Review section: each `## Review…` section (one per review round) holds exactly one `Verdict: accepted | accepted-with-changes | rejected` (bold and backticks allowed, case-insensitive) or `Status: awaiting review`, never both. A `rejected` or `accepted-with-changes` verdict needs at least one reason marked `**major**` or `**minor**`.
- A heading starting "Response" reads `Response (round n)` and has content (§7a.1.8 step 3).
- The file name is `<yyyy-mm-dd>-<item-id>-<slug>.md`.

Not linted (judgement, or timing the lint cannot know): the 3-attempt and 3-round limits, the non-convergence note, and "probably/flaky/timing" wording.

Records already on `main` are not linted unless they are staged again; 43 of the 46 records there on 2026-10-31 use older headings (`Cause → symptom chain`, `Verification`) or verdicts (`**ACCEPTED**`, `cause accepted`) and fail. An edit to one of them brings it to the format in the same commit. There is no list of exempt records.

Reverse: drop a rule from `lintRootCause`, or add a date cut-off in `lintRecord` to exempt records dated before 2026-10-31.

### DEC-0631 — The test-review record format

Origin: ai-proposed · Status: accepted · Affects: plan v0.2.0 §7a.1.9; `ai/implementation/test-reviews/README.md`; `scripts/lint-records.mjs`

§7a.1.9 asks for "the groups, the verdict per group, and its reasons" and the six reason codes, but gives no layout. The record has header fields `Item:`, `Change set:`, `Author:`, then `Reviewer:` (after review) or `Status: awaiting review` (before), and one `## Group: <reason-code> — <title>` section per group with `Cites:`, `Tests:`, `Verdict:` and `Reasons:`. A group's verdict uses the root-cause record's three values (`accepted`, `accepted-with-changes`, `rejected`) so both reviews read alike. `Cites:` is required for `code-removed`, `component-removed`, `behaviour-changed` and `test-was-wrong`; for `test-was-wrong` it names a root-cause record that exists in the working tree or the index. A second change set of the same item on the same day takes a suffix, `<yyyy-mm-dd>-<item-id>-2.md`.

Reverse: edit the README and `lintTestReview` together.

### DEC-0632 — Which files the commit hook lints

Origin: ai-proposed · Status: accepted · Affects: plan v0.2.0 §7a.2.5; `scripts/claude-commit-hook.mjs`

§7a.2.5 says the hook lints "the staged files". A PreToolUse hook runs before the command, so in `git add x && git commit` nothing of `x` is staged yet, and `git commit -a` or `git commit <paths>` commits files that are not staged either. The hook therefore lints the files the commit will hold: the staged files (added, copied, modified or renamed), plus the files the same command adds before its last `git commit` (`git add`/`git stage` with pathspecs, `-A`, `-u`), plus the tracked modified files `git commit -a` and `git commit <pathspecs>` take. It follows `cd`, `pushd`, `git -C`, `bash -c`/`sh -c`, environment prefixes and `env`; it does not read quoted text, comments or heredoc bodies as commands. Staged records are read from the index; files the command adds, and every file eslint and tsc check, are read from the working tree. A commit in a repository that is not a checkout of this one (no `scripts/claude-commit-hook.mjs` at its top level) is not checked (TS-18). Over-approximation (for example `git commit <paths>` also linting other staged files) can block a commit that would have been clean; it never lets one through unchecked.

Reverse: narrow `commitFiles` to `git diff --cached` only.

### DEC-0633 — Which linters the hook runs, and how

Origin: ai-proposed · Status: accepted · Affects: plan v0.2.0 §7a.2.5; `scripts/claude-commit-hook.mjs`

- **eslint** on every `.js/.mjs/.cjs/.ts/.mts/.cts/.jsx/.tsx` file of the commit, with the root `eslint.config.js` and `--no-warn-ignored`; the config's own scope decides which rules apply (today typescript-eslint's recommended rules on `packages/framework/{src,bin,test}`, the same files as `npm run lint`).
- **typecheck**: the three projects of `npm run typecheck` (framework, root, harness) that include a TypeScript file of the commit, in that order; all three when a root `tsconfig*.json` or one of the three project files changes. TypeScript outside them (apps, starter) is not in `npm run typecheck` and is not checked here either. Before the harness project, the hook runs `npm run build -w packages/framework`, because that project reads the framework's `dist` (without it, `tsc` fails with TS2307 on `@lago-morph/prototype-framework/testing`).
- **record lints**: `scripts/lint-records.mjs` (DEC-0630, DEC-0631) on root-cause and test-review records.

Every failing check is reported, not only the first.

Reverse: change `PROJECTS` or the eslint file pattern in the hook.

### DEC-0634 — How the hook is registered and when it blocks

Origin: ai-proposed · Status: accepted · Affects: plan v0.2.0 §7a.2.5, TS-12, TS-18; `.claude/settings.json`

The new root `.claude/settings.json` holds only the hook: a PreToolUse entry with matcher `Bash` running `node "$CLAUDE_PROJECT_DIR/scripts/claude-commit-hook.mjs"`, timeout 300 s (the framework build plus the three `tsc` runs took 67 s here at load 12, 2026-10-31). The script filters for `git commit` itself and returns at once for every other command. It blocks with exit 2 and the problems on stderr, which Claude Code shows to Claude. It fails closed: once it has found a commit, an error of its own, a missing `node_modules` (eslint or typescript not installed: "run npm ci") or a failed build blocks the commit. Input that is not hook JSON is let through. `--no-verify` does not skip it, since it is not a git hook; no file under `.git/hooks` is written. The template's `.claude/settings.json` is unchanged and has no hooks (TS-18).

Reverse: delete the `hooks` entry from `.claude/settings.json`.
