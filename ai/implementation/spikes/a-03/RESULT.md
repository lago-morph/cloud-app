# A-03 — Does an SST/Pulumi update of a Worker keep secrets set separately through the Cloudflare API?

> **Code and logs archived.** This spike's scripts, `logs/` and `out/` are on branch `archive/implement-local-cloudflare`, in the same directory (see ARCHIVE-INDEX.md there, and `ai/ARCHIVE.md`). The relative paths below resolve on that branch.

## Question

cloudflare.md "Deploy mechanics": "confirm that an SST/Pulumi update of the Worker script keeps the secrets set by `secrets set`. If it does not, the deploy keeps them through the Cloudflare API's handling of a script's existing secret bindings, never by storing a second copy of the secrets."

## Verdict

**Kept.** Every SST update of the Worker (new script content, changed plain-text variable, a removed binding, after `sst refresh`) kept the secret `SECRET_SPIKE` that was set through `PUT /accounts/{id}/workers/scripts/{name}/secrets`, and the running Worker still saw the same value. No fallback needed; nothing in SST config is needed for it.

**Mechanism (control experiment):** it is the Cloudflare script-upload API itself. A direct multipart `PUT /workers/scripts/{name}` whose metadata lists only other bindings and **no** `keep_bindings` leaves existing `secret_text` bindings in place (r01, step r3). `keep_bindings: ["secret_text"]` is accepted and behaves the same (r5); the SST transform `worker: args => { args.keepBindings = ["secret_text","secret_key"] }` is accepted by SST/Pulumi and deploys fine (s07) — a ready, explicit belt-and-braces option, not required today.

**Caveat (r02):** if a deploy declares any binding **with the secret's name** (e.g. a plain-text variable `SECRET_SPIKE`), the upload replaces the secret, and it is gone for good (not restored when the name is dropped again). The framework must never declare a `SECRET_<NAME>` binding through SST (environment/CFG variables must not use the `SECRET_` prefix).

### Additional findings for D-03 / every cloud run

1. **`sst remove` deletes the Worker and with it its secrets** (expected), and again leaves the stage's state objects (26 objects) in `sst-state` — confirms A-01.
2. **SST's Worker component with `url: true` needs `NODE_USE_ENV_PROXY=1`** in this sandbox. SST's own dynamic providers (`WorkerUrl`, also `kv-data`, `worker-placement`, `zone-lookup`; `.sst/platform/src/components/cloudflare/helpers/fetch.ts`) call `api.cloudflare.com` with Node's global `fetch` and `Authorization: Bearer $CLOUDFLARE_API_TOKEN`. Without `NODE_USE_ENV_PROXY=1`, Node's fetch ignores `HTTPS_PROXY`, so the placeholder is not replaced: s01 failed with `{ code: 9106, message: 'Authentication failed (status: 400)' }` on `/workers/scripts/spikeuekwqgqb-a03-apiscript/subdomain`. With it, s02 completed (Node prints a harmless `[UNDICI-EHPA] … EnvHttpProxyAgent is experimental` warning). This amends A-01's SST environment (A-01's KV-only app never reached a dynamic provider).
3. **`workers.dev` probes from Python `urllib` get HTTP 403 "error code: 1010"** from Cloudflare (bot signature ban on the default `Python-urllib` User-Agent), not from the proxy: curl to the same URL got 200, and the proxy's `recentRelayFailures` had no new entry (c07). Any non-browser test client should send its own User-Agent. Proxy refused no host during this spike.

A03_VARIANT=v1b  ENV_PROXY=1   ./sst.sh s05-deploy-v1b-after-refresh deploy
