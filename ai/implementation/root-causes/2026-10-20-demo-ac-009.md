# Root cause: DEMO-AC-009 clipboard test times out waiting for a link named /account/i (final local run)

Author: diagnosing subagent (prompt §8 step 1). I did not write the demo, the framework or the test involved. This is a diagnosis only: no code or test was changed. It needs an independent review (§8 step 2) before anyone fixes it.

Branch: `worktree-agent-a4f9d123033373eee`, reset to `claude/implement-local-cloudflare` `46612ec` (the final-local evidence merge). Demo: build round 4 (`97dd0d7`, `apps/demo/BUILD-RECORD.md`). ## Short answer

The test assumes the account page is reached through a link named like "Account". The round-3 demo had such a link; the round-4 demo, rebuilt from scratch, has none. It renders the account section (user ID and "Copy ID" button) inline on every page. `docs/demo/demo-spec.md` does not require a link, so the round-4 demo is compliant and the test's assumed flow is wrong. **The fix belongs to the test (compliance test author, fix-f4b's spec), not the demo or the framework.**

## Evidence

E1. **The test requires a link.** `tests/compliance/e2e/demo-pages.spec.ts:48` sets `ASSUMED_ACCOUNT_LINK = /account/i`; line 275 clicks `getByRole("link", { name: ASSUMED_ACCOUNT_LINK })` after `page.goto("/")` (line 274). Decision `ai/implementation/decisions/fix-f4b.md` (DEC-PENDING-fix-f4b-2) lists "account link | link | `/account/i`" among the **assumed** names, and DEC-PENDING-fix-f4b-3 says "The user reaches the account page through the page's own link".

E2. **The specification names no link or route for the account page.** `docs/demo/demo-spec.md:55-58` (DEMO-REQ-009): "The app has login and logout controls and an account page that shows the logged-in user's user ID, with a button to copy it". `docs/demo/demo-spec.md:84` (DEMO-AC-009): "The account page shows the same ID as `/api/auth/me`, and the copy button copies it." Neither says how the page is reached.

E3. **The round-4 demo has no account link; the account section is on every page.**
- `apps/demo/src/client/main.ts:41`: `root.append(accountPage(user));` runs for every route (after the post, share and list branches at lines 32–40).
- `apps/demo/src/client/pages/account.ts:6` heads the section "Account" (`section("Account")`, an `h2`, `dom.ts:13-16`); lines 18–29: a button "Copy ID" that calls `navigator.clipboard.writeText(user.id)`.
- The only `<a>` elements in `apps/demo/src/client` are the site title home link (`main.ts:20-21`), post-title links (`pages/post-list.ts:8-9`), photo download links (`pages/post-view.ts:18-19`) and the share URL (`pages/post-view.ts:80-81`). None can be named like "account" (the site title is "Photo board").

E4. **The round-3 demo, which the test was validated against, did have the link.** `git grep -i account 8c2af58 -- apps/demo/src/client`: `main.ts:18` `link("/account", "Account")` in a nav bar, and `main.ts:51` `if (path === "/account") root.append(accountPage(user))`. fix-f4b's red-green table ("Red-green non-vacuity (local, round-3 demo at `8c2af58`)") ran only against round 3, and DEC-PENDING-fix-f4b-2 ends: "The whole spec must be re-checked against the round-4 demo before the F-03 run." E6. **Experiment: the demo satisfies DEMO-AC-009 when the link step is removed.** A temporary, uncommitted copy of the spec (deleted after the run) identical except that line 275 (the link click) was removed and a log line added after the copy-button wait. Result, 1 passed (12.9 s):

## Chain (cause → symptom), with evidence for each link

1. The test hard-codes a navigation step that the specification does not require: click a link named /account/i (E1, E2).
2. The round-4 demo puts the account section on every page and has no such link (E3, E6 link list).
3. `getByRole("link", { name: /account/i })` therefore matches nothing, and `click({ timeout: 30_000 })` times out at line 275 (E5, symptom).
4. The test passed earlier only because round 3 happened to have the link (E4).

## Alternatives ruled out

- **Demo defect against demo-spec.** DEMO-REQ-009 and DEMO-AC-009 require an account page that shows the ID and a copy button that copies it; both are present and work (E3, E6). No link or route is specified (E2). A reviewer who reads "page" as "a separate route" would put the fix on the demo instead; demo-spec defines no routes for any page (the post list, drafts and post pages also have none named), so I read "account page" as the account view, as the test's own decision (fix-f4b-2, "found by role and accessible name with tolerant patterns") intends.
- **Framework.** The failure is a missing element on a page the app renders; `/api/auth/mock-login` (204) and `/api/auth/me` (200, correct ID) worked in both runs (E5, E6), and the dev server started and stopped normally.
- **Timing or load.** The element does not exist in the round-4 source at all (E3); the run in E6 found the page fully rendered (the copy button visible) and still only one link.
- **Clipboard permissions.** Not reached in the failing run; in E6 the permission grant, sentinel write/read and copy all worked.

## Which side is wrong

The test (`tests/compliance/e2e/demo-pages.spec.ts`, author: fix-f4b), and the assumption recorded in DEC-PENDING-fix-f4b-2/-3. Not the demo, not the framework.

## Proposed fix (minimal, red-green)

In `tests/compliance/e2e/demo-pages.spec.ts`, DEMO-AC-009 only (no change to DEMO-AC-001/-003, the demo or the framework):

- Make the account link optional, in the way the attach button already is (line 245): after `page.goto("/")`, if `getByRole("link", { name: ASSUMED_ACCOUNT_LINK })` has a match, click it and wait for load; otherwise stay on the current page, where the account view must then be shown. Then continue unchanged with the copy-button visibility wait, sentinel and clipboard assertion (lines 276–284).
- Update the comment at line 273, and DEC-PENDING-fix-f4b-2 (table row "account link … (optional; followed if present)") and -3 ("reaches the account view, through its link if the page has one").

Red: the current spec fails against round 4 (E5). Green: with the change, the experiment in E6 shows it passes.
