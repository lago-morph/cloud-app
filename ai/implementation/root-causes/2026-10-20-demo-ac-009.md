## Short answer

The test assumes the account page is reached through a link named like "Account". The round-3 demo had such a link; the round-4 demo, rebuilt from scratch, has none. It renders the account section (user ID and "Copy ID" button) inline on every page. `docs/demo/demo-spec.md` does not require a link, so the round-4 demo is compliant and the test's assumed flow is wrong. **The fix belongs to the test (compliance test author, fix-f4b's spec), not the demo or the framework.**

## Chain (cause → symptom), with evidence for each link

1. The test hard-codes a navigation step that the specification does not require: click a link named /account/i (E1, E2).
2. The round-4 demo puts the account section on every page and has no such link (E3, E6 link list).
3. `getByRole("link", { name: /account/i })` therefore matches nothing, and `click({ timeout: 30_000 })` times out at line 275 (E5, symptom).
4. The test passed earlier only because round 3 happened to have the link (E4).

## Alternatives ruled out

- **Demo defect against demo-spec.** DEMO-REQ-009 and DEMO-AC-009 require an account page that shows the ID and a copy button that copies it; both are present and work (E3, E6). No link or route is specified (E2). A reviewer who reads "page" as "a separate route" would put the fix on the demo instead; demo-spec defines no routes for any page (the post list, drafts and post pages also have none named), so I read "account page" as the account view, as the test's own decision (fix-f4b-2, "found by role and accessible name with tolerant patterns") intends.
- **Framework.** The failure is a missing element on a page the app renders; `/api/auth/mock-login` (204) and `/api/auth/me` (200, correct ID) worked in both runs (E5, E6), and the dev server started and stopped normally.
- **Timing or load.** The element does not exist in the round-4 source at all (E3); the run in E6 found the page fully rendered (the copy button visible) and still only one link.
- **Clipboard permissions.** Not reached in the failing run; in E6 the permission grant, sentinel write/read and copy all worked.

## Which side is wrong

The test (`tests/compliance/e2e/demo-pages.spec.ts`, author: fix-f4b), and the assumption recorded in DEC-0411/DEC-0412. Not the demo, not the framework.

**Verdict: accepted** (diagnosis and fix). No required changes. Two optional improvements are listed at the end.

### Cause

Correct, and every link of the chain is supported by the source.

- The specification names no link or route: `docs/demo/demo-spec.md:57` (DEMO-REQ-009) asks for "an account page that shows the logged-in user's user ID, with a button to copy it"; `docs/demo/demo-spec.md:84` (DEMO-AC-009) asks that it show the `/api/auth/me` ID and that the copy button copy it.
- The round-4 demo shows the account section on every route: `apps/demo/src/client/main.ts:41` appends `accountPage(user)` after all three branches (lines 32–40). `apps/demo/src/client/pages/account.ts:6` titles it "Account" through `section()`, which renders an `h2` (`apps/demo/src/client/dom.ts:11-14`); `account.ts:16` shows the ID in a `code` element; `account.ts:18-21` is the "Copy ID" button calling `navigator.clipboard.writeText(user.id)`.
- No link can match `/account/i`: the only `a` elements are `main.ts:20` (site title), `pages/post-list.ts:8`, `pages/post-view.ts:18` and `pages/post-view.ts:80`.
- The round-3 demo had the link: `git grep` on `8c2af58` shows `main.ts:18` `link("/account", "Account")` and `main.ts:51` the `/account` route, which is what fix-f4b's round-3 red-green ran against.
- So the old `tests/compliance/e2e/demo-pages.spec.ts:275` click had nothing to match and timed out, as in the symptom.

Alternatives: reading "page" as "separate route" would put the fault on the demo, but demo-spec defines no route for any page, so a demo change is not required by the specification; the record addresses this explicitly. Framework, timing and clipboard causes are ruled out by the source (the element does not exist in round 4) and by E6. The test was wrong, which §8 allows as a root-cause finding, and it went through the steps.

### Fix (`c3b407c`, `tests/compliance/e2e/demo-pages.spec.ts:262-296`)

Minimal and not weakened. Only the DEMO-AC-009 test and one constant (`:49`) change; `apps/demo` and the other two tests are untouched.

- Account heading: `:281` asserts `getByRole("heading", { name: /account/i })` is visible.
- Displayed ID: `:283` asserts `getByText(id, { exact: true })` is visible, where `id` comes from `/api/auth/me` (`:269-272`) and is itself pinned to the mock identity. This is a new assertion; the pre-fix test did not check the displayed ID at all, so the test is stronger than before.
- Exact clipboard content: `:288-293` are unchanged: a sentinel is written and read back first, then after the click the clipboard must equal `id` exactly (`toBe`).
- The link is followed only if present (`:276-280`), the same pattern as the optional attach button (`:245`). If an account view existed only behind a link not named `/account/i`, the heading or ID assertion fails rather than passing vacuously.

### Red-green and non-vacuity

Adequate.

- Red reproduces the recorded symptom at the same line; green runs the whole spec file (all three tests share the `beforeAll` dev server), against round 4 as committed.
- Check (i) removes the clipboard write (`account.ts:21`) and fails on the sentinel: it proves the clipboard assertion depends on the copy button.
- Check (ii) empties the ID `code` (`account.ts:16`) and fails on the exact text: it proves the new displayed-ID assertion is not satisfied by other text. `account.ts:14` can still contain the ID inside "Logged in as …", and exact matching correctly rejects it.
- Both breaks were temporary and reverted; `git diff apps/` was empty, and the commit touches no `apps/` file.

### Optional improvements (not required)

1. The heading and ID locators are page-wide with `.first()`. Scoping the ID and copy button to the region under the account heading would tie "the account page shows the ID" more tightly to the account section. On round 4 the only exact-text match is `account.ts:16`, so the present check is sound.
2. The heading assertion has no non-vacuity break of its own. It is a light anchor, and the two checks above cover the criterion's two clauses, so this is acceptable.
