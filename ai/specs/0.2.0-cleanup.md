### 1.1 Root files: does a tool require each one at the root?

| Root entry | Required at root? | By what |
|---|---|---|
| `package.json` | Yes | npm workspaces: the root manifest declares `workspaces`, and `npm ci` / `-w` resolve from it. |
| `package-lock.json` | Yes | npm writes one lockfile, at the workspace root. |
| `.github/` | Yes | GitHub Actions reads only `.github/workflows/` at the root. |
| `.claude/` | Yes | Claude Code project settings (the commit hook in `settings.json`) and project skills. |
| `CLAUDE.md` | Yes | Claude Code loads the project-wide instructions from the root. |
| `.claude-plugin/` | Yes | `/plugin marketplace add lago-morph/cloud-app` reads `.claude-plugin/marketplace.json` at the repository root. |
| `.gitignore` | Yes, for root paths | Git reads `.gitignore` in every directory, but only a root one can cover root `node_modules/` and `test-results/`. |
| `README.md` | No, by convention | GitHub also renders a README from `.github/` or `docs/`. Kept as the landing page (owner). |
| `LICENSE` | Yes, in practice | GitHub's licence detection reads the root. Each package keeps its own copy for npm. |
| `CHANGELOG.md` | No external tool | Only this repository's `release-check.mjs --notes` reads it, by path. Kept (owner). |

| `vitest*.ts` | No, but see risk R2 | Vitest takes `--config`. Without a root config, a bare `npx vitest run <path>` from the root runs with Vitest's 5 s/10 s defaults, which is what root cause `2026-10-24-data-api-fake-template-intermittent` fixed. |

| `eslint.config.js` | No | ESLint 10 resolves the flat config from each linted file's directory upward. |
| `QUICKSTART.md` | No | Owner-facing document. Moves to `docs/` (Q1). |
| `docs/`, `ai/` | No | Not in decision 1's list, but decision 4 defines `ai/`, and `CLAUDE.md` and every package README cite `docs/`. Both stay (Q2). |
| `scripts/`, `tests/`, `skill/`, `validation/` | No | Removed by this spec. |

### (c) The EPIPE crash

`packages/framework/test/fixtures/support/app.ts:215` `run()` calls `child.stdin.end(options.stdin ?? "")` with no `'error'` listener on `child.stdin`. **Fix:** `child.stdin.on("error", (e) => { if (e.code !== "EPIPE") stdinError = e; })` before `end`. The `close` handler resolves as today (exit code and output tell the story), or rejects with `stdinError` when it is set.

**Test:** `packages/framework/test/fixtures/support/app.unit.test.ts` (add `test/fixtures/**/*.unit.test.ts` to the framework unit globs). `run(process.execPath, ["-e", "require('fs').closeSync(0); setTimeout(() => process.exit(3), 200)"], tmp, { stdin: "x".repeat(1 << 20) })` resolves with `code: 3` and does not throw. The 1 MiB input exceeds the pipe buffer, so the write is still pending when the child closes stdin, and EPIPE is deterministic. It must be red before the fix. The same unguarded pattern is in six more helpers (Q10).

### (e) A name is metadata, never identity (owner decision, 2026-11-08)

**Decision:** the framework acts (reads to update, updates, deletes) only on resources whose IDs it recorded when it created them. A name is a label shown to people. Finding a resource by name never makes it the framework's.

**Today's defect:** the framework finds the tokens it manages by name, so any account token with the same name gets updated in place or deleted, including one a person made by hand:
- `packages/framework/src/provision/cloudflare/everyday-token.ts:43–55` (`tokensNamed`, name `prototype-framework`), used by `ensureEverydayToken` (:82, which PUTs new policies into every same-named token) and by `deleteOldEverydayTokens` (:120, which deletes any listed ID that bears the name).
- `r2-token.ts:240` (`createAccountSigningCredential`: every token named `prototype-r2-signing` is "old" and replaced).
- `r2-token.ts:297` (`findLegacySigningToken`: the per-stage name of DEC-0100, which `remove` deletes).

**Where the IDs go:** the account setup record `framework/account.json` in the `sst-state` bucket (`setup-record.ts`). This spec proposes it over Secrets Store:
- token and client IDs are not secret;
- the record is already read by setup, `deploy` and the admin app's setup and status pages, through the R2 object endpoints the everyday token can use;
- it already keeps unknown fields on write.

Secrets Store would need Secrets Store Read on every command that acts, and it holds values, not metadata. The new field is `managed`, shaped `{ "everydayTokens": [id], "signingTokens": [id], "oauthClients": { "admin": id, "signin": id }, "stageSigningTokens": { "<app>/<stage>": id } }`. It is parsed strictly; an invalid field reads as "none recorded". Written by the code that creates the resource, in the same run, right after the create succeeds. When a write fails, the run stops and names the new ID (as DEC-0729 does for the credential). Removed from the record when the framework deletes the resource.

**Rules:**
- **Everyday token:** `ensureEverydayToken` updates only recorded IDs that are still listed. With no recorded ID it creates a new token and records it. It never PUTs to an unrecorded token. `deleteOldEverydayTokens` deletes only recorded IDs (still never the last one) and drops them from the record.
- **Account signing credential:** `createAccountSigningCredential` replaces only `signingTokens`.
- **Legacy per-stage signing token:** `remove` deletes it only when recorded. 0.1.x never recorded these (see the migration).
- **OAuth clients** (same principle): `ensureOAuthClients` (`oauth-clients.ts:108`) today deletes every client named `CLIENT_NAMES[kind]` whose ID the Secrets Store entries' comments do not name (DEC-0684, DEC-0685). Instead, record the client IDs in `managed.oauthClients`. Keep a client only when its recorded ID is listed and both entries name it. Delete only a recorded client. Never delete a same-named one that is not recorded.
- **Safe uses stay:** setup's write guard learns `prototype-r2-signing` tokens by name (`cloudflare-setup.ts:243`), but only to refuse writes to them. Using a name to protect something is not using it as identity.

**Migration for installs with no `managed` field** (every 0.1.x and 0.2.0-rc install):
- Nothing is adopted automatically.
- The admin app's Everyday token page and Account setup page list the same-named tokens and clients they find. They show each one's name, ID, creation date (`issued_on`/`modified_on`) and whether its policies are exactly the framework's set. The signed-in admin ticks the ones that are the framework's, and the page records those IDs. Unticked ones are left untouched, with a line: "not created by the framework as far as it knows: delete it in the dashboard if it is unused".
- Non-interactive paths (`cloudflare-setup`, `setup-account`, `remove`) never adopt. They act as if nothing is recorded: they create new resources and record them. They print each same-named unrecorded resource with the dashboard path. `remove` leaves a legacy per-stage signing token in place and says so.
- A one-line CHANGELOG `Changed` entry explains the change to existing users.
- `ACCOUNT_SETUP_VERSION` goes up by one, so existing accounts are sent once through the page that offers adoption.

**Tests (red first):**
- Unit, `everyday-token.unit.test.ts`: a same-named unrecorded token is neither PUT nor deleted, and a new one is created and recorded; recorded IDs are updated; a recorded ID no longer listed is dropped from the record; `deleteOldEverydayTokens` skips a same-named unrecorded ID.

Every export's JSDoc starts with its `PAR-nnn:` or with `Tunable (not registered):`. The files import nothing, so Workers can import them. `admin-app/params.ts` and `auth-app/params.ts` move in. The app-facing limits (PAR-215, 223, 230, 233, 234) are exported publicly, so `apps/*` import them instead of copying them.
- `packages/create-prototype-app/lib/parameters.mjs`: PAR-290. The package has no runtime dependencies, so it keeps its own copy, and a test checks that copy against the framework's.
- `apps/compliance/harness/parameters.ts`: the harness PARs (270, 280, 284–286, 310). It imports the framework's values where they are shared (291).
- `tooling/live-pass/lib/parameters.mjs`: the runner checks the published release, so its expected values (PAR-413, 425, 435, 437) stay local, with a unit test asserting they equal the framework's source.

**Overridable per deployed stage:** through the stage config's existing `framework` section (`config/<target>/<stage>.json`, validated by CFG), as `framework.parameters.<name>`. Each overridable parameter has a lower and an upper bound in its constants file. The production stage refuses overrides of security values unless they are explicitly confirmed (Q18). Proposed list:
- PAR-425 role re-check interval, which the owner wants short for live testing;
- PAR-426/427 role-refresh retries and delay;
- PAR-445 admin-app session, and PAR-446 admin-app grant;
- PAR-250 session lifetime;
- PAR-233 transfer-ticket lifetime (a short value would have made §6(b)'s real wait cheap);
- PAR-416 sign-in transaction.

Not overridable: platform limits (PAR-202, 216–219, 245), pins, names, and the PAR-435 bootstrap bound (§6(d)).

**Checks (feasible):**
1. `packages/framework/src/parameters/register.unit.test.ts` parses `docs/parameters/parameters.md` and fails when a registered value and its constant differ, or when an active PAR has no constant and no "enforced by" note.
2. `@typescript-eslint/no-magic-numbers` on `packages/framework/src/**`, excluding `src/parameters/**` and tests, with only `-1, 0, 1, 2` and array indexes allowed. HTTP status codes move to `src/parameters/http.ts`, or come from an `HttpStatus` map.
3. `tooling/par-literals.mjs` plus its test. It lists each active PAR's distinctive values (numbers of three or more digits in their written forms, such as `900_000`, `900000` and `15 * 60_000`; strings of six or more characters, such as the role names, URLs and token names) and fails when one appears outside the constants files and tests. It runs in `npm run lint` and in the commit hook.
Check 2 catches new numeric literals in general, and check 3 catches literals that copy a PAR's value. Neither can catch a value spelled a new way (`5 * 60` versus `300`); the review rule in testing-standards covers that gap.

**Tests and records:**
- The register test above.
- Each overridable parameter: a CFG schema unit test (bounds, production refusal) and one integration test showing that the override takes effect.
- Existing tests import the constants, except one register test per package, which keeps the literal values.
- A DEC (Origin: owner, 2026-11-08), "No hard-coded values; per-stage overrides".
- `docs/components/config.md` gains the `framework.parameters` section (owner wording, as Q12).
- The register gains a "Constant" column and an "Overridable" column.

## 7. Risks

- **R1 Workflows.** Agents cannot push `.github/workflows/*`. Mitigation: batch 0c makes the workflows call only root npm scripts, so the moves need no workflow change. Batch 6 needs one more owner install.
- **R2 Bare Vitest runs.** Without a root config, `npx vitest run <path>` from the root uses 5 s/10 s defaults and reintroduces the intermittent PGlite timeouts. Mitigation: each unit config sets `UNIT_RUNNER`, and testing-standards says: run tests from the unit directory or through the npm scripts, never a bare root `npx vitest`.
- **R3 Ignore files.** The root `.gitignore` ignores `packages/create-prototype-app/template/`, and `packages/prototype-framework-skill/.gitignore` ignores `skill/`. Either would silently drop new files from the moved trees. Both are fixed in their batches (4, 5).
- **R4 Tarball contents.** The template, now packed in place, could carry `node_modules`, `.framework`, `dist` or `test-results` from local runs. The skill package must still unpack to `package/skill` for users' setup scripts (`cp -r package/skill …`). Mitigation: `.npmignore`/`files` negations and the pack-diff checks.
- **R5 Lockfile churn.** Workspace keys move. Regenerate with `npm install` and check that only path keys changed (no version drift).
- **R6 Published links.** The 0.1.x/0.2.0 READMEs on npm and the plugin `homepage` link to `blob/main/{QUICKSTART.md,skill/SKILL.md,apps/template/README.md}`. Those links go dead (Q11).
- **R7 Evidence removal.** The traceability report and any doc citing a removed run folder (for example `pass-2to5/` and `pass-1c/`, cited by the decision log and the skill) lose their target in `main`. Mitigation: the archive branch at original paths and an "Archived" line, as done twice before (`ai/ARCHIVE.md`).
- **R8 Binding docs.** The layout is DEC-0049 and `cli.md` §2, and `compliance.md` names paths. Changing them needs owner-approved wording (Q12).
- **R9 Merge conflicts.** Every open branch conflicts. Freeze merges for the duration.
- **R10 ESLint 10 config lookup.** Files with no config above them make ESLint fail. Lint only framework paths, in both the hook and `npm run lint`.

Restructuring `apps/demo` or `apps/reference`. The `aws` branch. Deleting remote branches (`ai/reports/branch-cleanup.md`). Publishing or tagging.
