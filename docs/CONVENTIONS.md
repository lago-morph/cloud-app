# Documentation Conventions

These conventions govern every document under `docs/`. They exist so that requirements, decisions, parameters, contracts, and tests can be traced to each other and changed safely.

## 1. What is binding

Only text inside an **identified requirement** (an item with a `*-REQ-*` ID) or an **identified contract file** under `docs/contracts/` is normative. Everything else — overviews, rationale, examples, notes, design discussion — is informative. An informative sentence never becomes a rule by being phrased firmly.

Within a requirement, MUST / MUST NOT / SHOULD / MAY have their RFC 2119 meanings.

Design documents describe how a component intends to meet its requirements. An implementer may deviate from a design detail that is not a requirement, a contract, or an `owner` parameter, provided the deviation is recorded in the decision log.

## 2. Identifiers

Identifiers are durable. Once published they are never renumbered or reused. A retired item keeps its ID and is marked `Status: retired` (with a pointer to its replacement, if any).

| Item | Format | Example |
| --- | --- | --- |
| System requirement | `SYS-REQ-NNN` | `SYS-REQ-004` |
| Component requirement | `<AREA>-REQ-NNN` | `KV-REQ-003` |
| Component acceptance criterion | `<AREA>-AC-NNN` | `KV-AC-007` |
| End-to-end scenario | `E2E-NNN` | `E2E-002` |
| Decision | `DEC-NNNN` | `DEC-0012` |
| Parameter (limit, timeout, default, pin) | `PAR-NNN` | `PAR-014` |
| Error code | `<AREA>.<NAME>` (upper snake case) | `KV.INVALID_KEY` |

`<AREA>` is a component code from [architecture/component-map.md](architecture/component-map.md). Component codes are themselves durable identifiers.

## 3. Traceability

Traceability links are written in **one direction only: the child names its parent.** Reverse views (parent → children) are generated by tooling, never maintained by hand, so the two directions cannot drift.

| Child | Names its parent with |
| --- | --- |
| Component requirement | `Derives from: SYS-REQ-…` |
| Component acceptance criterion | `Verifies: <AREA>-REQ-…` |
| End-to-end scenario | `Verifies: SYS-REQ-…` |
| Automated test | A tag containing the `*-AC-*` or `E2E-*` ID(s) it covers |
| Requirement or parameter with a recorded decision | `Decision: DEC-…` |

Every `SYS-REQ` must be verified by at least one `E2E` scenario or by component acceptance criteria whose requirements derive from it. Every component requirement must be verified by at least one acceptance criterion.

## 4. Origin (provenance)

Every requirement, decision, parameter, and end-to-end scenario carries an **origin**:

| Origin | Meaning | Who may change it |
| --- | --- | --- |
| `owner` | Stated by the owner. | Only the owner. |
| `owner-approved` | Proposed by an AI, explicitly approved by the owner. | Owner approval required. |
| `ai-proposed` | Proposed by an AI as a design choice; not reviewed by the owner. | An implementer, with a decision-log entry. |
| `provenance-unclear` | Inherited from earlier AI-assisted work; origin cannot be established. Treat as `ai-proposed`. | An implementer, with a decision-log entry. |
| `derived` | A consequence of other decisions, not a choice in itself. | Changes when its sources change. |

**End-to-end scenarios** (`acceptance/e2e-scenarios.md`) carry their origin on an `Origin:` line after the `Where:` line. The scenarios that existed on 2026-10-31 carry `Origin: ai-proposed (reviewed by the owner before 2026-10-31)`, and a new scenario carries `Origin: ai-proposed`. For scenarios, the following rule replaces the table's last column: agents may add, change and retire E2E scenarios of any origin, to match the framework's current intent. Each such change needs a decision-log entry, and no owner approval. How to make the change is in the testing-standards skill (§8).

## 5. Parameter categories

Parameters (limits, timeouts, sizes, defaults, version pins) live in [parameters/parameters.md](parameters/parameters.md), never inline in design text. Design text refers to them by ID. A parameter is added only when a component design or contract actually uses it. Spec-level requirements and decisions do not reference concrete parameter values; concrete values come from component designs (DEC-0057). Each parameter has one category:

| Category | Meaning | Change policy |
| --- | --- | --- |
| `owner` | Set by the owner. | Only the owner. |
| `platform` | Imposed by a cloud platform or dependency; cites its source. | Re-verify against the source; update when the platform changes. |
| `ai-proposed` | Chosen by an AI; no external basis required. | Free to change during implementation and testing; record the new value. |

## 6. Contract formats

| Interface kind | Format | Location |
| --- | --- | --- |
| HTTP endpoints | OpenAPI 3.1 | `docs/contracts/http/` |
| Data formats (config manifest, cookies, evidence files, …) | JSON Schema 2020-12 | `docs/contracts/schemas/` |
| In-process TypeScript APIs | `.d.ts` declarations with behavior in the owning component's design document | `docs/contracts/ts/` |

A contract file is the single source of truth for the shape of its interface. Design documents describe behavior and refer to contract files; they do not restate signatures.
