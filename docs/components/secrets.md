# SEC — Secrets

Secret values read by logical name: storage on each target, setting values without exposing them, and the framework's own internal secrets.

Contracts: [secrets.d.ts](../contracts/ts/secrets.d.ts), [errors.d.ts](../contracts/ts/errors.d.ts) (`SEC.*`).

## 1. Requirements

#### SEC-REQ-001 — Declared names only
Origin: owner-approved · Derives from: SYS-REQ-015

App code MUST read only secrets declared in its app definition; other names fail with `SEC.UNDECLARED`. A declared secret with no value in the stage fails with `SEC.MISSING`.

#### SEC-REQ-002 — Values stay secret
Origin: owner-approved · Derives from: SYS-REQ-015

Secret values MUST NOT appear in the repository, configuration files, build output, browser bundles, log entries, or error responses.

#### SEC-REQ-003 — Storage per target
Origin: owner-approved (storage); ai-proposed (locations) · Derives from: SYS-REQ-015

Secret values MUST be stored as follows (DEC-0012):

| Target | Storage | Location of secret `<name>` |
| --- | --- | --- |
| Local | Git-ignored `.dev.vars` file | `SECRET_<NAME>` |
| Cloudflare | Worker secrets | `SECRET_<NAME>` |
| AWS | SSM Parameter Store SecureString | `/<app>/<stage>/secrets/<name>` |

#### SEC-REQ-004 — Setting values
Origin: provenance-unclear · Derives from: SYS-REQ-015

The CLI MUST let the owner set a secret for a target and stage with the value read from standard input, never from command-line arguments or files in the repository.

#### SEC-REQ-005 — Availability
Origin: provenance-unclear · Derives from: SYS-REQ-010

An unreachable secret store MUST surface as `SEC.UNAVAILABLE`. A value read from AWS MAY be cached for at most PAR-240; a missing value MUST NOT be cached.

## 2. Design

**Names.** Logical names are lowerCamelCase in code. `<NAME>` is the upper snake case form.

**Framework-internal secrets** use the reserved prefix `framework`, which app declarations cannot use. They are:
- the session signing key, generated by the CLI per stage when absent (AUTH);
- the Google client secret (GOOGLE);
- the R2 signing credentials, created by provisioning (FILES);
- the per-deploy migration credential on Cloudflare (MIG).

The Data API's database credentials are the one exception to SEC-REQ-003's AWS row. The Data API requires them to be in AWS Secrets Manager, so provisioning creates them there. Neither app code nor SEC reads them (DEC-0061).

**Local.** Missing framework-internal development secrets are generated into `.dev.vars` on first `dev`; existing values are never overwritten.

**AWS.** `GetParameter` with decryption, using the Lambda role. The role is granted read access to the stage's `/<app>/<stage>/secrets/` path only.

## 3. Uses

CFG (declared names and resolved locations), CLI (setting values), PROV (IAM permissions, Worker secret bindings).

## 4. Acceptance criteria

| ID | Criterion | Verifies | Where |
| --- | --- | --- | --- |
| SEC-AC-001 | A declared secret with a value is returned; an undeclared name fails with `SEC.UNDECLARED`; a declared name without a value fails with `SEC.MISSING`. | SEC-REQ-001 | Local, cloud |
| SEC-AC-002 | A scan of the repository, the build output, the deployed browser assets, the stored log entries, and error responses from a test run finds no test secret value. | SEC-REQ-002 | Local, cloud |
| SEC-AC-003 | After a secret is set with the CLI, it exists at the specified location on each target. The AWS Lambda role cannot read another stage's secrets. | SEC-REQ-003 | Local, cloud |
| SEC-AC-004 | The CLI rejects a secret value supplied as a command-line argument. | SEC-REQ-004 | Local |
| SEC-AC-005 | A secret deleted on AWS is reported missing within PAR-240; a newly set secret is seen within PAR-240. | SEC-REQ-005 | Cloud |

## 5. Portability note

The contract is "read string by name". A new target needs only a store addressable by name and a convention for that name.
