# COMPL — Compliance suite

One contract test suite and a reference app, run identically on every target; evidence recording; and the definition of when the framework "works".

Contracts: [evidence.schema.json](../contracts/schemas/evidence.schema.json).

## 1. Requirements

#### COMPL-REQ-001 — One suite, every target
Origin: owner-approved · Derives from: SYS-REQ-026

A single test suite MUST verify each component's acceptance criteria against the reference app on local, Cloudflare, and AWS. Cloud runs use test stages. The same tests MUST run on every target where a criterion applies, with no per-target expectations except those a criterion states.

Note (informative; SYS-REQ-026 as amended, DEC-0508): release 1 runs the suite on local and Cloudflare. The AWS target is deferred (branch `aws`): `npm run compliance` refuses `--target aws`, and a criterion that applies only on AWS is expected on no release target.

#### COMPL-REQ-002 — Traceability
Origin: owner-approved · Derives from: SYS-REQ-026

Each test MUST be tagged with the acceptance-criterion or scenario IDs it covers. A generated report MUST list each criterion and scenario with its tests and results, and MUST flag any that have no tests.

#### COMPL-REQ-003 — Evidence
Origin: provenance-unclear · Derives from: SYS-REQ-028

Each run on each target MUST write an evidence record conforming to the schema. Each result is `passed`, `failed`, `blocked` (a prerequisite was missing), or `not-run`; a criterion not executed is never recorded as `passed`. A `blocked` or `not-run` result MUST state the reason in `detail`. When a failure came from an HTTP response, its `detail` MUST include the observed status, error code, and requestId. The runner MUST refuse to record evidence from a working tree that differs from the recorded commit.

#### COMPL-REQ-004 — Disposable cloud runs
Origin: provenance-unclear · Derives from: SYS-REQ-024 · Decision: DEC-0081

Cloud runs MUST use test stages named `test-<run ID>`, where the run ID contains enough randomness that the stage's name and public address cannot be guessed. They MUST always attempt to remove those stages afterwards, and MUST record any leftover resources in the evidence record. The leftover check MUST cover every resource in PROV's removal list, including a stage's legacy R2 API token (DEC-0550). The production-check stage (§2) is exempt from this requirement (naming and removal).

Amendment (Origin: ai-proposed · Decision: DEC-0560): criterion production stages are an exception to the `test-<run ID>` naming. A stage-lifecycle criterion that needs a production stage of its own (PROV-AC-003's production removal, PROV-AC-004's production deploy) names it with a reserved prefix and 10 random lowercase letters and digits (`p003…`, `p004…`; `CRITERION_PRODUCTION_PREFIXES` in `tests/compliance/harness/criterion-stages.ts`). Before it deploys one, the test writes a marker `compliance/criterion-stages/<stage>.json` (`{ stage, runId, createdAt }`) in the state home, and it deletes the marker after the stage's successful removal. Such stages are cleaned like test stages, but only when marked and stale: at the start and at the end of every cloud run the driver removes each stage whose marker is older than PAR-286 (the longest criterion run) with `remove --confirm-production <stage>`, deletes the marker once nothing of it remains, and records what remains, or a listing that fails, as a leftover. A stage with a fresh marker (another run's) is left alone, and a stage of the reserved shape without a marker is only reported as a warning. No other production stage is ever removed.

## 2. Design

**Reference app.** `apps/reference/` exposes small routes exercising each capability feature. It uses only the public exports, like any app. Framework-level scenarios run against it, not against the demo. Its fixtures include:
- a route that throws a plain `Error`;
- a route that writes a log entry;
- a route that sets two cookies;
- committed version 1 and version 2 schemas, and a data fixture, for E2E-010 and MIG-AC-003. The change between them uses only the supported changes listed in MIG §2.

**Two layers of tests.** HTTP-level tests run from the driver in `tests/compliance/` against a base URL. Browser-level tests (file transfers, cookies) use Playwright. SQL dialect tests also run in-process against local D1 and PGlite.

**Playwright projects.** Browser criteria of the framework suites and the compliance criteria are in the project `integration`. The E2E scenarios' tests are in two projects (from item S3, which replaces the single `e2e` project):
- `e2e-api`: tests that drive the HTTP API, the CLI or both, through Playwright's `request` fixture or a plain HTTP client. They launch no browser. Most scenario tests are here.
- `e2e-ui`: the few tests of what only a browser shows, such as page rendering, sign-in pages, file transfer in the page, and cookies.

Of these projects, only `e2e-ui` and `integration` launch a browser; outside Playwright, so does the template-pages browser test `tests/skill/example-pages.test.ts`. Chromium is installed only for a run that selects a test that needs one.

**Comparisons.** Query results without a total ordering are compared as multisets. Floating-point comparisons use PAR-280.

**Time limits.** Each cloud wait has a bounded timeout derived from the platform behavior it waits for, such as database resume (PAR-210).

**Tiers.** Automated criteria and scenarios form the automated tier. Where they run (CI selection from item S3):
- **Pull requests:** framework CI (`.github/workflows/ci.yml`) runs the local integration and e2e layers when the change selects them, by the committed path map `scripts/ci/path-map.json`. A component's integration suite and criteria run when the component, or a component it depends on, changes. The e2e projects run when application behaviour changes. A PR that changes only docs or specs runs neither layer. The one exception is the short list of docs that tests read: the path map names the tests for each, and only those run, never an e2e test.
- **Release:** `.github/workflows/release.yml` runs every test once on the version tag, including all integration tests and both e2e projects.
- **Cloud passes:** the compliance driver runs the automated tier on Cloudflare, outside GitHub Actions, which holds no cloud credentials.

Selection on pull requests does not change COMPL-REQ-006: a commit works only when every automated criterion and scenario has passed for that commit on every applicable target.

Milestone items (COMPL-REQ-006) run only when an event invalidates their latest record, never on a clock. Invalidation entries are lines in `validation/invalidations.md`, each with the date, the affected item IDs, and the reason.

**Test stages.** A run's test stages are named `test-<run ID>` (PROV-REQ-005). The run ID is generated from a cryptographically secure random source and fills the rest of the stage name allowed by PAR-291 with lowercase letters and digits; a stage-lifecycle criterion that needs further stages generates a further random ID of the same form for each. Each run uses one test stage per cloud for every criterion that does not concern stage lifecycle. Stage-lifecycle criteria create and remove their own stages. The leftover check looks for each resource of PROV's removal list by its exact name, using `listStageResources` (per-target operations: PROV §2). The driver calls the framework's own Cloudflare operations in its process, wired as `remove` wires them, so behind a proxy the driver itself is started with `NODE_USE_ENV_PROXY=1`; without it, or without credentials, the check fails before any request and the evidence records that failure as a leftover (DEC-0357).

**Production-check stage.** Each cloud has one long-lived production stage of the reference app named `prodcheck`. Its committed values file is `config/<target>/prodcheck.json`; it needs no login-provider settings, and its secrets (`frameworkSessionKey`, `frameworkAuthSecret`) are generated by the CLI. The suite redeploys it on every run, and compliance cleanup never removes it. Like every production stage, its deploy registers its return URL with the account's auth app (PROV-AC-002). It serves COMPL-REQ-005, E2E-006, and `check-login --target <cloud> --stage prodcheck` (AUTH-AC-011 and the automated part of E2E-008), which the driver runs after the test layers. `check-login` works over HTTP only: it follows the login redirect to the auth app's `/start`, sends a callback with a bogus code and reads `/api/auth/me` after it, and asks that `/start` whether the return URL is registered; it needs no Cloudflare credential, signs nobody in and leaves no user or role behind (DEC-0670). The owner's once-per-release real sign-in, the live parts of E2E-007 and E2E-008, is made on `prodcheck` too (plan-v0.2.0 §7, "Live"; DEC-0692). Roles come from the Cloudflare account (DEC-0690), so no test grants one there (DEC-0700; the `admins grant` steps of DEC-0526 are gone with the `admins` command).

**Testers.** Every criterion in which a tester follows documented steps is performed by an AI agent (DEC-0512), with one exception: the once-per-release real sign-in, the live parts of E2E-007 and E2E-008, in which the owner signs in on Cloudflare's own login page (SYS-REQ-027 as amended by DEC-0692).

Amendment for v0.2.0 (Origin: owner-approved · Decision: DEC-0699): the owner's once-per-release live pass also covers the setup steps that need the owner in the dashboard or the admin app: making the bootstrap token, and signing in to the admin app for account setup and the everyday token (plan-v0.2.0 §1 D9, D10, §5.1, §5.2; SKILL-AC-006, SETUP-AC-011). The owner may override this in a session.

**Driver.** `npm run compliance -- --target <local|cloudflare> [--stage <test-…>] [--milestone] [--base-url <url>] [--only <ID,…>] [--blocked <ID,…|*>=<reason>]…` (`tests/compliance/harness/`) refuses to start from a working tree whose tracked files differ from HEAD. It derives the expected IDs for the target and tier from the Where columns and lines, plus this phase's not-run rules. It builds and type-checks, then starts `dev` for the reference app or deploys one `test-<run ID>` stage. On a stage it deploys, it then generates a random value (32 letters and digits) for the reference app's test secret `apiKey`, holds it in memory only, sets it with `secrets set apiKey --target <cloud> --stage <stage>` (value on standard input), and deploys again: the first deploy of a new stage stops on the unset secret with the app stopped. The tests receive the value in `COMPLIANCE_SECRET_API_KEY`; the evidence writer, the raw output, the driver's own output and the live echo of the test runners replace it with `<test-secret>` (DEC-0277, D-07). Locally the value stays where the operator set it, `apps/reference/.dev.vars`. It runs each selected test layer once, selecting only the tests tagged with an expected ID: the integration layer and the Playwright projects, and on local also the unit layer for the unit-level criteria only, whose unit test outcomes count only for those IDs (DEC-0319). It writes one record through the evidence writer (`<package>/src/evidence/`, shared with `smoke`). On a cloud it removes the stage and runs the leftover check. Results are recorded, not judged. A criterion with a failing tagged test is `failed`, with the first failure line in `detail`. A criterion whose test reported a missing prerequisite, or which the operator named with `--blocked`, is `blocked` with the reason. One with no executed tagged test is `not-run`, and each skipped tagged test adds a `not-run` entry. Stages a run could not remove are kept in a local pending list, and the next cloud run removes them first. A leftover, a leftover check that could not run, a `dev` that did not stop, or a pending-stage list that could not be updated makes the run exit non-zero, keeping any earlier non-zero status (CLI-REQ-003). Only `test-` stages are ever removed. The traceability and release reports are `node tests/compliance/tools/report.mjs traceability|release`. Decisions: DEC-0259…DEC-0266, DEC-0319, DEC-0320. Release 1 (DEC-0508): `--target aws` is refused as deferred (branch `aws`), and the AWS usage caps and region step of DEC-0501/DEC-0503 are on that branch. The traceability report shows local and Cloudflare results and lists AWS-only criteria as deferred, never as untested.

**Cloud account at the start and end of a run (Cloudflare).** Before it deploys, the driver reads the account's Workers plan (`GET /accounts/<account>/subscriptions`, else `COMPLIANCE_CLOUDFLARE_PLAN`, else Free), logs the plan's D1 budget (PAR-284 or PAR-285), and passes the plan to the tests in `COMPLIANCE_D1_PLAN`, whose database guard applies that plan's cap (DEC-0530). For each selected clause that needs a restricted credential and whose variable the operator did not set, it creates an account API token named `prototype-compliance-<run ID>-<kind>` that lacks the permission under test, with an expiry of PAR-286. The tokens model DEC-0551's everyday and setup tokens (`tests/compliance/harness/test-tokens.ts`): PROV-AC-002's is the everyday token itself (no permission on API tokens; `no-r2-token`); PROV-AC-003's is the everyday token with "Workers R2 Storage Read" instead of "Write", so a production `remove` cannot write its backup (`no-r2-write`); PROV-AC-004 has three: the setup token without "Email Routing Addresses Write" (`no-email`), the setup token with "Account API Tokens Read" instead of "Write" (`no-tokens-write`), and the everyday token without "Email Sending Read" (`no-sending-read`). It holds the value in memory, passes it only to the test processes, and redacts it as `<test-token>` like the test secret. At the end of the run, also after a failure, it deletes those tokens, and every `prototype-compliance-*` token the account still lists is a leftover (DEC-0531). At the start it deletes such tokens an interrupted earlier run left. The cloud test hooks' R2 tokens (`compliance-r2read-<run ID>-<12 hex>`, `compliance-r2scoped-<run ID>-<12 hex>`, each with a 30-minute expiry; `tests/compliance/criteria/_cloud/r2.ts`) are cleaned up the same way. These sweeps, like everything in this paragraph, run only on a cloud run with cloud account access (`DriverDeps.cloudAccount`; not on a self-test) that selects at least one criterion to run. At the start of such a run, and at its end (also after a failure, including a failed setup), the driver deletes every such token that is expired or older than an hour, and at the end also every one named with its own run ID, whose test processes have all ended; it never deletes another run's unexpired token younger than an hour. A failed plan read or stale-token deletion does not skip the start sweep. Names without a run ID (`<prefix><12 hex>`, the form before the run ID was added) are deleted only once expired or older than an hour; a token whose name does not have exactly one of these shapes (an owner's `compliance-r2read-notes`) is never touched. Every such token still listed after the end sweep is a leftover, including another live run's unexpired token, so a run that overlaps another run's reports that run's tokens. A driver killed before its end sweep leaves its tokens to the next run's start sweep, by which time they have expired.

**Tokens the harness is given** (Origin: orchestrator, pending owner review · Decision: DEC-0604). The operator supplies the account's everyday token in `CLOUDFLARE_API_TOKEN` and the account in `CLOUDFLARE_ACCOUNT_ID`, in the environment of the driver, as before the setup wizard. The harness reads no `.env.cloudflare` and writes none; the framework commands it runs get its environment, which wins over any `.env.cloudflare` in the app's folder (DEC-0570). It removes `CLOUDFLARE_BOOTSTRAP_TOKEN` from every child process's environment, except for a milestone clause of SETUP-AC-011 that needs the bootstrap token, which the owner supplies for that run only. The harness keeps creating its own restricted test tokens (DEC-0531, `test-tokens.ts`) for each clause that needs a token lacking a permission, including the everyday-shaped token that SETUP-AC-011 takes a permission away from and setup restores. Every `cloudflare-setup` run it starts gets the owner's everyday token ID in `PROTOTYPE_FRAMEWORK_PROTECTED_TOKEN_IDS` (PAR-361, DEC-0589), so setup's guard refuses to update or delete it. It never deletes or edits a token it did not create: the owner's everyday token, any other dashboard token and the account's `prototype-r2-signing` token are only read (and the signing token replaced only by `setup-account` in PROV-AC-004's milestone clause, as before). The bootstrap token's self-deletion is the one exception, and only for a token the owner made and handed over for that clause. `cloudflare-setup`'s automated criteria (SETUP-AC-001…010) run against the fake Cloudflare API with fake token values only.

**Account-changing milestone clauses** (DEC-0560). PROV-AC-002's signing-credential clause and PROV-AC-004's token and re-run clauses change the account's signing record or lifecycle rules; they run in milestone passes only, restore what they changed in a `finally`, read it back, and fail the run loudly, naming `setup-account --target cloudflare` with the setup token, when the restore does not hold. PROV-AC-004's re-run clause replaces the account's R2 signing token `prototype-r2-signing`; every deployed stage keeps the old credential until its next deploy, so the milestone pass that runs it must have no other stage up: the clause first lists the account's Workers and refuses (blocked) while any exists besides the mail sink, the reference app's `prodcheck` and the reference app's marked criterion production stages. After the replacement it redeploys `prodcheck` (when it exists), so its Worker holds the new credential, and shows an upload and a download through its tickets. If the credential is broken when the clause ends, it writes the old record back while the old token still exists, and otherwise fails naming the repair command. Run it in a pass of its own with no run stage: `npm run compliance -- --target cloudflare --milestone --only PROV-AC-004 --base-url https://unused.invalid`.

**Deploy recovery.** A runner-only abort point lets the suite stop a deploy after the database copy or after the code deploy (PROV-REQ-002 step 5), so a re-run can be checked.

## 5. Portability note

The suite is one set of tests for every target (COMPL-REQ-001): the Where columns select the criteria that apply, and per-target expectations exist only where a criterion states them. A new target adds its value to the driver's `--target` and to the evidence schema's `target` enumeration (component map §1), brings its own `prodcheck` stage and values file (COMPL-REQ-005) and its own component's criteria, and its leftover check uses that target's `listStageResources` (PROV §2). Existing tests do not change.
